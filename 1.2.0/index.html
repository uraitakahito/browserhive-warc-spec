This specification profiles [[WARC]]. It states which records BrowserHive writes into a WARC file and what each of them holds, so that a reader holding only the file can tell what the capture recorded, what it left out, and why.

This is a working draft. It describes what BrowserHive writes today. It has no standing beyond that project and is not endorsed by the publishers of [[WARC]].

Up to its version 1.15.0, [[BROWSERHIVE-WACZ-PROFILE]] held the rules for the WARC records BrowserHive writes. They moved here so that a WARC file can name the rules it follows by itself (see ), and so that a file read apart from its package still means what it says. BrowserHive WACZ Profile 1.22.0 requires the WARC files of a package to conform to this version.

[[WARC]] defines a WARC-Profile header field, which says how a revisit record is to be read. This specification has nothing to do with that field.

Introduction

[[WARC]] says how records are framed and which header fields they carry. It leaves to the writer what to put in a payload, which records to write about a body it did not keep or a request it did not send, and how to say why. A reader of a BrowserHive WARC file needs those answers, and they are knowable only while the file is being written.

This profile fixes them. It changes nothing [[WARC]] requires, and a redacted record, which holds less than [[WARC]] recommends, says so in its own fields (see Conformance). Most of the records it adds are metadata records, which a reader unaware of this profile can pass over. A snapshot is recorded in a resource record as well, under a URI of its own, and that record is meant for such a reader: one that serves archived pages lists it and serves it like a page it holds, showing the page as it stood when the snapshot was taken.

BrowserHive writes its WARC files into a WACZ package, whose rules are in [[BROWSERHIVE-WACZ-PROFILE]]. The rules here concern only what a single WARC file holds, so that they still hold for a file taken out of its package.

Conformance

The conformance target of this specification is a WARC file: a single file. Conformance is a property of files, not of the software that writes them.

A conforming file is a conforming [[WARC]] file. This specification adds requirements. It removes none, and it relaxes none.

A redacted record departs from what [[WARC]] says of a record, and says so in its own BrowserHive-Redacted field. [[WARC]] recommends that a request record block contain the full HTTP request sent over the network and a response record block the full HTTP response received over the network; a redacted record holds that message with values replaced. [[WARC]] also has WARC-Target-URI be the original URI; in a redacted record, as in the other records whose URI has a value replaced (see ), it is that URI with values replaced.

Where this specification uses the terms MUST, MUST NOT, SHOULD and MAY, they are to be interpreted as described in [[RFC2119]].

The producer is the software that writes the file. A capture is one run of the producer against one page. A capture writes one or more WARC files.

The warcinfo record

Each WARC file MUST begin with a warcinfo record whose WARC-Filename is the name of the file that holds it. Its application/warc-fields body MUST contain the fields below marked as required.

FieldRequiredDescription
conformsToyes The URL of the version of this specification the file claims to satisfy. For this version, https://uraitakahito.github.io/browserhive-warc-spec/1.2.0/. The field MUST appear exactly once.
formatyes WARC File Format 1.1.
softwareyes The producer and its version.
robots-policyno ignore: the producer does not consult robots.txt. Whether a page is to be captured at all is for whoever asks for the capture to decide.
descriptionno Free text that says what was captured.
 
WARC/1.1
WARC-Type: warcinfo
WARC-Record-ID: <urn:uuid:0b7e8a52-6a63-4f0e-9d0b-6f1c2a3e4d5f>
WARC-Date: 2026-11-01T02:14:31.882Z
WARC-Filename: data-000.warc.gz
Content-Type: application/warc-fields
Content-Length: 203

software: browserhive/29.0.0
format: WARC File Format 1.1
conformsTo: https://uraitakahito.github.io/browserhive-warc-spec/1.2.0/
robots-policy: ignore
description: Capture of https://shop.example/

conformsTo names this profile, not [[WARC]]. The base format is named by format, and every conforming file is a WARC 1.1 file (see Conformance). A single declaration leaves a reader nothing to choose between. A reader MUST NOT infer conformance to a version of this specification from anything other than conformsTo.

Records and files

A record MUST NOT span two files: a record is written whole into one file, and the producer writes no continuation records. The records of one exchange MUST be in the same file, and so MUST the two records of one snapshot.

A capture may write more than one file. How those files are named, and when the producer starts a new one, are rules of the package that holds them, not of a single file. See [[BROWSERHIVE-WACZ-PROFILE]].

Exchanges

An exchange is one request the browser sent and the response it received to it. The producer records an exchange as a request record and a response record, and, when the response is recorded without its body, a record of a body not kept. The request record and the response record MUST each name the other in WARC-Concurrent-To.

The records of one exchange MUST carry the same WARC-Date: the time at which the browser began the request, as the browser reported it. A response that redirects ends its exchange. The request that follows the redirect begins another exchange, with its own time.

The payload of a response record MUST be in HTTP/1.1 form [[RFC9112]], whatever protocol version carried the exchange: a status line, then the header fields, then the body.

[[WARC]] has the date of a record be the moment its capture began, and has the records of one capture event share one date. For an exchange, that moment is when the browser began the request. The time at which the producer assembles the records is later by however long the body took to arrive, which for a large body can be minutes, and it says when the producer wrote rather than when the page was fetched.

Existing readers of WARC files parse the payload of a response record as HTTP/1.1. An exchange carried over HTTP/2 or HTTP/3 is therefore written in HTTP/1.1 form, and the protocol version that carried it is not recorded in the payload.

Payloads

A browser turns a text body into characters before anything else sees it, and hands it to tools as characters. Written back out as bytes, the result is the body in whatever encoding the writer chose — not the one the origin sent, unless the two happen to agree. The requirements in this section keep the payload of each record to the bytes that crossed the wire, so that a payload digest vouches for what the origin and the browser sent. The exception is a redacted record whose BrowserHive-Redacted field names payload: values in its payload were replaced, and its payload digest vouches only for the bytes the record holds.

Response payloads

The payload of a response record that holds a body MUST be the bytes the server sent, with the content-coding named in its Content-Encoding removed and nothing else changed, except for what a redacted record replaces (see ). In particular, a producer MUST NOT convert a text body from one character encoding to another: a body sent in Shift_JIS is stored as those Shift_JIS bytes, and a body whose media type declares no charset is stored as it was sent, whatever charset a browser would have read it with.

A data: URL is sent by no server. Its payload is the data the URL carries, decoded as the URL defines (base64, or percent-encoding as bytes), and likewise not converted, with the same exception for what a redacted record replaces.

A producer that cannot obtain a body as bytes MUST NOT store one rebuilt from decoded text. It records the response with an empty payload and a record of a body not kept whose truncated is not-intercepted.

Request payloads

The payload of a request record that holds a body MUST be the bytes the browser sent as the request body, except for what a redacted record replaces (see ). A producer that cannot obtain them as bytes MUST NOT store a body rebuilt from decoded text; it records the request without one.

Redacted records

A secret is a value that whoever asked for the capture supplied in confidence, for behaviors to read. A hidden secret is a secret that whoever asked for the capture did not ask to keep. Its value is at least eight characters long: a producer refuses a request that gives a shorter value without asking to keep it. Which secrets a capture was given, and which of them were kept, are recorded in the settings of the package that holds the file ([[BROWSERHIVE-WACZ-PROFILE]]).

In each request and response record, the producer MUST replace each occurrence of the value of a hidden secret with the three characters ***, in WARC-Target-URI, in the request line, in the values of HTTP header fields and in a text body. A record in which it replaced one is a redacted record. Where one occurrence contains another, the producer replaces the longer, and each *** it writes is one replacement.

An occurrence is a form of the value that the producer recognizes: the value as it is, in UTF-8, or one of these spellings of it.

  • Percent-encoded as encodeURIComponent encodes it, as an application/x-www-form-urlencoded body encodes it, or as a URL's path or query encodes it, with the hexadecimal digits in upper or lower case.
  • In a JSON string, with only the escapes JSON requires.
  • In HTML, with &amp;, &lt;, &gt;, &quot; and &nbsp; for the characters they stand for, and &#39;, &#x27; or &apos; for an apostrophe.
  • The base64 of the value alone.
  • The whole of the encoded credentials of HTTP Basic authentication, which hold the value once decoded.
  • The whole of the data of a data: URL in base64, which holds the value once decoded.
  • In the value of a header field, any of these with each byte of its UTF-8 read as one Latin-1 character, which is how a browser reports a field that came in UTF-8.

The producer MUST NOT write an occurrence anywhere else in the file. In the WARC-Target-URI of any other record, it replaces occurrences in the same way.

A WARC-Target-URI stays a URI, which [[WARC]] requires and which has to have a scheme. Where replacing takes away the scheme of the URI, as it does when a value begins with it, the producer MUST write that scheme and a colon in front of the result: with the value https://shop.example/a, the URI https://shop.example/a?b=c becomes https:***?b=c.

A response to a request that held an occurrence may set a cookie that stands in for the secret. When the producer observes such a response, and a Set-Cookie header field of it sets a cookie whose value is at least eight characters long, the producer MUST treat that value as the value of a hidden secret from the moment that response arrives, including in the record of that response and in this rule.

A redacted record MUST carry a BrowserHive-Redacted field in its WARC record header, which says where the producer replaced values and how many times: 

BrowserHive-Redacted: target-uri=1, headers=1, payload=2

The field holds one part for each place in which the producer replaced at least one occurrence, in the order of this table, and no part for any other place:

PartWhat it counts
target-uri Replacements in WARC-Target-URI. The request line repeats the same occurrences, and they are not counted again.
headers Replacements in the values of HTTP header fields.
payload Replacements in the body.
 
BrowserHive-Redacted = "BrowserHive-Redacted" ":" redacted-part *( "," SP redacted-part )
redacted-part        = part-name "=" part-count
part-name            = "target-uri" | "headers" | "payload"
part-count           = 1*DIGIT   ; in decimal, 1 or more, with no leading zero

[[WARC]] allows a field of this kind: its File and record model section lets extensions define new named fields, and the General part of its Named fields section has software ignore a field whose name it does not recognize. A request or response record without this field MUST NOT have any value replaced: it holds what the rest of this specification says it holds. A record of any other type MUST NOT carry this field, even where it has a value replaced in its WARC-Target-URI, and a reader cannot tell *** there from the same characters in the URL.

In this excerpt of a redacted request record, values of hidden secrets were in the query, in a header field and twice in the form the page posted: 

WARC-Type: request
WARC-Target-URI: https://shop.example/login?key=***
Content-Type: application/http;msgtype=request
BrowserHive-Redacted: target-uri=1, headers=1, payload=2

POST /login?key=*** HTTP/1.1
Host: shop.example
Content-Type: application/x-www-form-urlencoded
Content-Length: 32
X-Api-Key: ***

user=alice&password=***&note=***

For the rules of this section, a text body is a body whose media type is one of these. The media type of a response body is the one the browser determined for it, and that of a request body is the one its Content-Type header field declares.

  • text/*;
  • JSON: application/json and any type ending in +json;
  • XML: application/xml, application/xhtml+xml and any type ending in +xml;
  • JavaScript: application/javascript, application/ecmascript, application/x-javascript and application/x-ecmascript;
  • application/x-www-form-urlencoded.

When a body that is not a text body holds an occurrence, the producer MUST NOT replace inside it: a change in its length would break it. The producer records the message without that body, and the record MUST carry WARC-Truncated: secret; the WARC-Truncated section of [[WARC]] allows extensions to define other reasons. A response recorded this way also has a record of a body not kept whose truncated is secret. A record of that kind describes only a response, so a request has WARC-Truncated: secret alone. Dropping a body replaces nothing, so it counts in no part of BrowserHive-Redacted: a record in which nothing else was replaced carries WARC-Truncated and not BrowserHive-Redacted. 

WARC/1.1
WARC-Type: metadata
WARC-Record-ID: <urn:uuid:a41d7e20-9b3c-4f15-8e62-5c0a7d3b1f94>
WARC-Target-URI: https://shop.example/export?key=***
WARC-Date: 2026-11-07T02:14:31.882Z
WARC-Refers-To: <urn:uuid:7c2e4b19-3f6a-4d08-8a51-2b9d0e6f1c37>
Content-Type: application/warc-fields
Content-Length: 44

truncated: secret
encodedDataLength: 4821

In a redacted record, and in a record from which the producer dropped a body, Content-Length, WARC-Block-Digest and WARC-Payload-Digest, and the Content-Length header field of the HTTP message if it has one, MUST describe the bytes the record holds. The producer MUST NOT write, in either digest field, a digest of the bytes before replacement or of the dropped body: with the bytes the record holds, such a digest would let a reader test guesses of the value.

A value made from a secret, such as a hash or a ciphertext, is not an occurrence, and neither is a credential an origin newly issues in a response body, such as a token in JSON. This specification does not claim that a file holds none of them.

Records of bodies not kept

For each response recorded without the body the server sent, other than a response that has no body to send (one to a HEAD request, and status 1xx, 204, 3xx and 304), the file that holds the response record MUST also hold a metadata record, hereafter a record of a body not kept. Its WARC-Target-URI MUST be the URL of the response, with the value of any hidden secret replaced (see ), its WARC-Refers-To MUST be the WARC-Record-ID of the response record, and its application/warc-fields body MUST contain:

FieldRequiredDescription
truncatedyes Why the record holds no body. One of the values below.
encodedDataLengthno The size of the whole response as it crossed the wire, in bytes, when the producer knows it.
  • too-large — the body was larger than the limit the producer placed on a single body.
  • task-cap — keeping the body would have taken the bodies the capture kept past the limit the producer placed on all of them.
  • url-policy — a URL policy of the producer said to keep the exchange without its body.
  • content-type — a media type policy of the producer said to keep no body of the response's media type.
  • not-intercepted — the body crossed the wire, but the producer could not obtain it as bytes (see ).
  • secret — the body was not a text body and held the value of a hidden secret (see ).
WARC/1.1
WARC-Type: metadata
WARC-Target-URI: https://example.com/api/feed
WARC-Date: 2026-10-30T02:14:31.882Z
WARC-Refers-To: <urn:uuid:5c1f0b8e-2a77-4a5e-9d3e-0f6f3b1d2c4a>
Content-Type: application/warc-fields
Content-Length: 53

truncated: not-intercepted
encodedDataLength: 4821

The response record of a body dropped at a size limit (too-large or task-cap) MUST carry WARC-Truncated: length, that of a body that was not intercepted MUST carry WARC-Truncated: unspecified, and that of a body dropped for holding the value of a hidden secret (secret) MUST carry WARC-Truncated: secret, so that a reader of the WARC file alone does not take the empty payload for the body.

A body a policy omitted was not cut short, so its response record carries no WARC-Truncated. Which limits and policies were in force is recorded outside the WARC file, by the package that holds it ([[BROWSERHIVE-WACZ-PROFILE]]).

Records of withheld requests

For each request the producer withheld by a policy, a WARC file of the capture MUST contain a metadata record, hereafter a record of a withheld request. Its WARC-Target-URI MUST be the request URL, with the value of any hidden secret replaced (see ), and its application/warc-fields body MUST contain:

FieldRequiredDescription
actionyes What the producer did. deny: it did not send the request, so nothing left the capturing machine for that URL. no-archive: it let the request go and the origin answered, but it kept nothing of the exchange beyond this record. This is the field that says whether the request was sent.
patternyes The pattern that matched, spelled exactly as the producer's policy spells it, so that a reader can find it there.
methodyes The request method.
resourceTypeno What the page was fetching, when the capture knows it.
targetno What made the request: page, iframe (a frame the browser runs apart from the page, typically one from another site), worker or service_worker. Absent when the capture does not say.
 
WARC/1.1
WARC-Type: metadata
WARC-Target-URI: https://www.example-analytics.com/collect?v=2
WARC-Date: 2026-09-06T02:14:31.882Z
Content-Type: application/warc-fields
Content-Length: 87

action: deny
pattern: *://*.example-analytics.com/*
method: POST
resourceType: XHR

A deny reaches every request the capture causes, so its record MUST be written whichever part of the page made the request, including parts whose traffic the producer does not otherwise record.

A record of a withheld request carries no response and no body. It asserts that the page asked for the URL and that the producer decided what to do about it — not that the request failed, and not that the origin returned nothing. A capture that could not reach an origin MUST NOT report it this way.

A policy that keeps the exchange but not its body produces no record of this kind. The request and response records are written as usual, and the absent body is reported by a record of a body not kept whose truncated is url-policy — never as dropped at a size limit.

Records of windows not opened

A capture records one page, and the producer does not give the page a new top-level browsing context — a window or a tab ([[BROWSERHIVE-WACZ-PROFILE]]). For each time the page asked for one, a WARC file of the capture MUST contain a metadata record, hereafter a record of a window not opened. Its WARC-Target-URI MUST be the URL the window would have loaded, as the browser reported it, with the value of any hidden secret replaced (see ): about:blank when the page named none, and the action URL, without the submitted body, when a form asked. Its application/warc-fields body MUST contain:

FieldRequiredDescription
windowyes not-opened. This version defines no other value.
windowNameno The name the page gave the window; _blank when it gave none. Absent when the page asked through a navigation that names no window, such as a click carrying a modifier key.
targetno What asked: page, or iframe (a frame the browser runs apart from the page, typically one from another site). Absent when the capture does not say.
 
WARC/1.1
WARC-Type: metadata
WARC-Target-URI: https://shop.example/campaign?from=top
WARC-Date: 2026-10-01T02:14:31.882Z
Content-Type: application/warc-fields
Content-Length: 54

window: not-opened
windowName: _blank
target: page

No request was sent for the window's document, so nothing left the capturing machine for that URL. The record is written whether or not a URL policy of the producer matches the URL, and it carries no action: it is not a record of a withheld request, and a reader MUST NOT count it as one.

Snapshots

A snapshot is a copy of the document in the page's main frame as it stood at one moment of the capture. The producer makes it from the document as the browser then holds it, with whatever scripts had changed in it, and not from anything a server sent. Each snapshot is taken at one of these stages:

  • after-load — the page has loaded and settled, and no behavior has run on it.
  • after-behaviors — the behaviors the capture ran on the page have finished.

A behavior is code that a capture runs on the page besides the page's own, for instance to fill in a search form and send it. A capture takes at most one snapshot at each stage, and none at after-behaviors unless it ran a behavior. The code of the behaviors, which stages a capture took, and why it took none at a stage are recorded by the package that holds the file ([[BROWSERHIVE-WACZ-PROFILE]]).

The producer records a snapshot as two records, written together: a resource record that holds the copy, and a metadata record that says what the copy is. The two records MUST NOT carry WARC-Concurrent-To. A snapshot is not part of an exchange, and [[WARC]] gives the records that field links one date, which a snapshot does not share with the exchange that loaded its document.

The resource record

The resource record of a snapshot holds the copy as its block, and MUST carry these header fields:

FieldRequiredDescription
WARC-Target-URIyes urn:browserhive:snapshot:, then the stage, a colon, and the URL of the document at the moment of the snapshot without its fragment, with the value of any secret replaced (see ): for instance urn:browserhive:snapshot:after-load:https://shop.example/. A page can change the URL of its document through the History API without loading another document, so the URL need not be the one the document was loaded from.
WARC-Dateyes The moment the producer took the snapshot.
Content-Typeyes text/html; charset=utf-8.
WARC-Block-Digestyes The digest of the block.
WARC-Payload-Digestyes The digest of the payload. For a resource record the payload is the block [[WARC]], so this digest is computed over the same bytes.
 
WARC/1.1
WARC-Type: resource
WARC-Record-ID: <urn:uuid:d6874c5c-9710-40d4-9fb8-ceb24bb0dfc8>
WARC-Target-URI: urn:browserhive:snapshot:after-behaviors:https://shop.example/results
WARC-Date: 2026-11-02T01:20:07.415Z
Content-Type: text/html; charset=utf-8
WARC-Block-Digest: sha256:RK4XPNMRVNTPF7OWYGYRXMHDFC5H2RF7BH74Y2KKIRRELLG6MZJQ
WARC-Payload-Digest: sha256:RK4XPNMRVNTPF7OWYGYRXMHDFC5H2RF7BH74Y2KKIRRELLG6MZJQ
Content-Length: 237

<!DOCTYPE html>
<html lang="en"><head><base href="https://shop.example/results">
<meta charset="utf-8"><title>Results for lamp</title></head>
<body><form role="search"><input name="q" value="lamp"></form>
<h1>3 results</h1></body></html>

Here a behavior searched the page for lamp. The page showed the results and changed its URL from https://shop.example/ without loading another document. What the behavior typed into the search field is in the copy, as the field's value attribute, and the base element that opens the head is the producer's (see ).

[[WARC]] keeps an http or https target URI of a resource record for what was returned for that URI, and offers a synthesized target URI for other artefacts of a harvest. A snapshot is such an artefact. Under a URI of its own, no reader takes it for what a server returned for the document's URL, and a reader that serves archived pages does not confuse it with the response for that URL, whatever their times.

The metadata record

The metadata record of a snapshot says what the copy is. Its WARC-Refers-To MUST be the WARC-Record-ID of the snapshot's resource record, its WARC-Target-URI and WARC-Date MUST be those of that record, and its application/warc-fields body MUST contain:

FieldRequiredDescription
snapshotyes The stage at which the producer took the snapshot: after-load or after-behaviors.
document-uriyes The URL of the document at the moment of the snapshot, as the browser held it, fragment included, with the value of any secret replaced (see ).
document-recordno The WARC-Record-ID of the response record that delivered the document, angle brackets included. That record may be in another file of the capture. Absent when the capture holds no such record.
secrets-replacedyes How many times the producer replaced the value of a secret in the copy, in decimal (see ). 0 when it replaced none. A replacement in document-uri or WARC-Target-URI is not counted.
 
WARC/1.1
WARC-Type: metadata
WARC-Target-URI: urn:browserhive:snapshot:after-behaviors:https://shop.example/results
WARC-Date: 2026-11-02T01:20:07.415Z
WARC-Refers-To: <urn:uuid:d6874c5c-9710-40d4-9fb8-ceb24bb0dfc8>
Content-Type: application/warc-fields
Content-Length: 158

snapshot: after-behaviors
document-uri: https://shop.example/results
document-record: <urn:uuid:3d6b2f0e-8c1a-4b7e-a2f4-6e9d1c5b8a07>
secrets-replaced: 0

In the example, document-uri is the URL the page changed to, and document-record names the response record that delivered the document from https://shop.example/.

The body MUST NOT carry action, truncated or window, and a reader MUST NOT count the record as a record of a withheld request, a record of a body not kept or a record of a window not opened. The record carries no WARC-Payload-Digest, which [[WARC]] allows only on a record with a well-defined payload.

What a snapshot holds

The block of a snapshot's resource record is the document serialized as HTML by the producer, encoded in UTF-8. It is the producer's work and not a server's, and a reader MUST NOT take it for what an origin sent. What the origin sent for the document is in the response record that document-record names, apart from what the producer replaced or dropped there for a hidden secret.

The first element in the head of a snapshot MUST be a base element whose href attribute is the document base URL at the moment of the snapshot, without its fragment: the URL against which the page resolved relative URLs, which is the URL of the document unless the page set another with a base element of its own. A reader serves the copy under the snapshot's own URI, and this element has the relative URLs in it resolve as they did in the page.

A snapshot MUST NOT contain the page's scripts: it holds no script element of any namespace, no attribute whose name begins with on, no srcdoc attribute, whose document could hold either, and no javascript: URL other than javascript:void(0) in an href, xlink:href, src, action, formaction or data attribute.

In a snapshot, an input element whose type is password MUST NOT carry a value attribute, whatever the field held.

A snapshot MUST NOT contain the value of a secret, hidden or not, neither as it is nor with its characters escaped as the HTML serialization escapes them (& as &amp;, for instance). The producer replaces each occurrence, in the href of the base element as anywhere else in the copy, and counts the replacements in secrets-replaced.

Making a snapshot

A producer can meet these requirements, and keep the copy close to what the page showed, as follows:

  • Read the document from a script context of its own (an isolated world, in Chromium), where the page's scripts cannot change how the document is read.
  • Copy the document and write into the copy what the page holds outside its markup: the current value of each field as its value attribute, or as the content of a textarea; which boxes are checked and which options are selected; each open shadow root as a template element with a shadowrootmode attribute; the style sheets the page adopted, as style elements; and each canvas as an image of what it showed. A canvas whose pixels the page could not read stays empty, and a password field gets no value.
  • Remove script and noscript elements, and link elements that preload scripts (rel="modulepreload", or rel="preload" with as="script"). Remove event handler attributes and srcdoc, and replace javascript: URLs with javascript:void(0), which keeps a link looking like a link.
  • Leave each frame's src as it is. The documents of frames are not part of the snapshot, and a reader shows what the capture recorded at those URLs.
  • Keep the document's doctype as it was, or its absence, so that a reader renders the copy in the page's mode.
  • Put the base element first in the head of the copy, with the document base URL the page used.
  • Serialize the copy, then replace each secret in the result, as it is and escaped, and each hidden secret in its other spellings too, with ***.

Security and privacy considerations

A WARC file holds what crossed the wire, apart from what this specification has the producer replace or leave out. Its request records hold the header fields the browser sent, which may include cookies and credentials, and its response records hold what the origins returned, including any personal data in it.

A record of a withheld request holds the URL of a request that was never sent, and a record of a window not opened holds the URL of a document that was never loaded. Both URLs may carry identifiers in their query strings. Withholding a request keeps it from the origin; it does not keep its URL out of the file.

A snapshot holds the text of the page as it stood, with what the page's scripts and the capture's behaviors had put into its fields: the value of every field but a password field is in the copy. The producer replaces the values of secrets it finds there, at least as they are and as HTML escapes them, and those of hidden secrets in every spelling lists. A secret the page had transformed otherwise may stay, for instance one hashed, and so may anything nobody declared a secret. The document-uri of a snapshot keeps the fragment of the document's URL, which is never sent to a server and which some sign-in flows use to hand a token to the page.

A redacted record hides the value of a hidden secret where the producer recognizes it: in what the browser sent and what the origins returned, in URLs, header fields and text bodies, and in a cookie set in answer to it. The producer drops a body it cannot edit (see ). Replacing a value changes the records and nothing that happened in the capture, and these stay as they were:

  • The page. A behavior hands the value to the page, where the page's scripts can read it and send it anywhere, and the origins it is sent to receive it.
  • What is made from the value. The producer does not follow a hash or a ciphertext computed from it, a digest in an HTTP header field such as Content-Digest, or a credential an origin issues in a response body, such as a token in JSON, which may open what the secret opened. A cookie of at least eight characters, set in a response the producer observes, is the only thing it follows.
  • A spelling that is not an occurrence, such as a value with non-ASCII characters in a body in another character encoding, or the value inside a longer base64 string.
  • A secret that is not hidden. The value of a secret that whoever asked for the capture asked to keep stays in the request, response and metadata records, though not in a snapshot.
  • The fact that a value was there. BrowserHive-Redacted says where and how many times, and what surrounds ***, such as the name of a form field, stays.

Replacing can also reach further than the secret. Any text that matches a value is replaced, and a body that is not a text body and holds it is dropped, whether or not the text has anything to do with the secret. A cookie makes this more likely: a value such as accepted counts as a hidden secret once a response has set it in answer to one, and a later request that sends it can bring in others the same way.

A reader unaware of this profile sees *** as what was sent, and the digests of a redacted record match what it holds, so a digest does not show the replacement. Whoever relies on a record for what crossed the wire needs to read BrowserHive-Redacted as well.

Whoever passes a file on passes all of this on. Beyond what a snapshot leaves out, and what the producer replaces or drops for a hidden secret, this specification does not ask the producer to remove any of it. What a capture keeps out of its records is decided by the policies of the capture, which the package that holds the file records ([[BROWSERHIVE-WACZ-PROFILE]]).
