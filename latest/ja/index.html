これは BrowserHive WARC Profile 1.1.0 の日本語訳です。正典は 英語原典であり、判断の根拠にする場面ではそちらを確認してください。 訳と原典が食い違った場合は原典が優先します。

本仕様は [[WARC]] のプロファイルです。BrowserHive が WARC ファイルにどのレコードを書き、 それぞれが何を持つかを定めます。ファイルだけを手にした読み手が、その取り込みが何を記録し、 何を残さず、それがなぜかを判断できるようにするためです。

これは作業中の草案です。BrowserHive が現在書き出しているものを記述しています。同プロジェクト 以外での位置づけを持たず、[[WARC]] の発行者から承認されたものでもありません。

BrowserHive が書く WARC のレコードの決まりは、[[BROWSERHIVE-WACZ-PROFILE]] の 1.15.0 までは、その中にありました。ここへ移したのは、WARC ファイルが自分の従う決まりを自分で 名乗れるようにするため（ を参照）、そしてパッケージから取り出して 読んだファイルも同じ意味を保つようにするためです。BrowserHive WACZ Profile 1.17.0 は、 パッケージの WARC ファイルがこの版に適合することを求めます。

[[WARC]] は WARC-Profile というヘッダの欄を定めており、それは revisit レコードの読み方を述べます。本仕様は、その欄とは関係がありません。

Introduction

[[WARC]] は、レコードの枠の作り方と、レコードが持つヘッダの欄を定めます。payload に何を 入れるか、残さなかった本文や送らなかったリクエストについてどのレコードを書くか、そしてその 理由をどう述べるかは、書き手に委ねています。BrowserHive の WARC ファイルの読み手にはその答えが 要り、それはファイルを書いている間にしか知りえません。

本プロファイルはそれを定めます。[[WARC]] の述べることは何も変えません。本プロファイルが 足すレコードの多くは metadata レコードで、本プロファイルを知らない読み手は 読み飛ばせます。写しは、それ自身の URI の下で resource レコードでも 記録し、そのレコードはそうした読み手のためのものです: アーカイブしたページを配る読み手は、 それを一覧に載せて手持ちのページと同じように配り、写しを取ったときのページの姿を見せます。

BrowserHive は WARC ファイルを WACZ パッケージに書き込み、パッケージの決まりは [[BROWSERHIVE-WACZ-PROFILE]] にあります。ここで定めるのは 1 本の WARC ファイルが持つ ものだけです。パッケージから取り出したファイルにも、そのまま当てはまるようにするためです。

Conformance

本仕様の適合対象は WARC ファイル、すなわちファイル 1 つです。適合はファイルの性質であって、 それを書くソフトウェアの性質ではありません。

適合するファイルは、適合する [[WARC]] ファイルです。本仕様は要求を追加します。 取り除くことも、緩めることもしません。

本仕様における MUST（〜しなければならない）、 MUST NOT（〜してはならない）、 SHOULD（〜すべきである）、 MAY（〜してもよい）は、[[RFC2119]] の記述どおりに解釈します。

producer は、ファイルを書くソフトウェアです。取り込みは、1 つの ページに対する producer の 1 回の実行です。1 つの取り込みは、1 本以上の WARC ファイルを 書きます。

The warcinfo record

各 WARC ファイルは、WARC-Filename がそのファイル自身の名前である warcinfo レコードで始まらなければなりません（MUST）。 その application/warc-fields の本文は、下の表で必須とした欄を含まなければ なりません（MUST）。

Field必須説明
conformsToはい そのファイルが満たすと主張する本仕様の版の URL。この版では https://uraitakahito.github.io/browserhive-warc-spec/1.1.0/。この欄は ちょうど 1 回現れなければなりません（MUST）。
formatはい WARC File Format 1.1。
softwareはい producer とその版。
robots-policyいいえ ignore: producer は robots.txt を見ません。ページを そもそも取り込むかどうかは、取り込みを求める側が決めることです。
descriptionいいえ 何を取り込んだかを述べる自由な文。
 
WARC/1.1
WARC-Type: warcinfo
WARC-Record-ID: <urn:uuid:0b7e8a52-6a63-4f0e-9d0b-6f1c2a3e4d5f>
WARC-Date: 2026-11-01T02:14:31.882Z
WARC-Filename: data-000.warc.gz
Content-Type: application/warc-fields
Content-Length: 203

software: browserhive/23.0.0
format: WARC File Format 1.1
conformsTo: https://uraitakahito.github.io/browserhive-warc-spec/1.1.0/
robots-policy: ignore
description: Capture of https://shop.example/

conformsTo が名指すのは本プロファイルで、[[WARC]] ではありません。基底の形式は format が名指し、適合するファイルはどれも WARC 1.1 のファイルです （Conformance を参照）。名乗りが 1 つなら、読み手はどちらを取るか迷いません。読み手は、 conformsTo 以外の何かから、本仕様のある版への適合を推し量ってはなりません （MUST NOT）。

Records and files

1 つのレコードが 2 つのファイルにまたがってはなりません（MUST NOT）。 レコードは 1 つのファイルに丸ごと書かれ、producer は continuation レコードを 書きません。1 つの交信のレコードは、同じファイルに在らなければならず （MUST）、1 つの写しの 2 つのレコードも同じです （MUST）。

1 つの取り込みが、2 本以上のファイルを書くことがあります。それらのファイルの名前と、 producer がいつ新しいファイルを始めるかは、ファイルを収めるパッケージの決まりで、1 本の ファイルの決まりではありません。[[BROWSERHIVE-WACZ-PROFILE]] を参照してください。

Exchanges

交信は、ブラウザが送った 1 つのリクエストと、それに対して受け取った レスポンスです。producer は交信を request レコードと response レコードで記録し、レスポンスを本文なしで記録したときは、さらに body not kept のレコードを書きます。request レコードと response レコードは、WARC-Concurrent-To で互いを名指さなければ なりません（MUST）。

1 つの交信のレコードは、同じ WARC-Date を持たなければなりません （MUST）。その値は、ブラウザがリクエストを始めた時刻で、ブラウザが 知らせたとおりのものです。redirect するレスポンスは、その交信を終えます。redirect の後に 続くリクエストは、自分の時刻を持つ別の交信を始めます。

response レコードの payload は、交信を運んだプロトコルの版に関わらず、 HTTP/1.1 の形 [[RFC9112]]（ステータス行、ヘッダの欄、本文の順）でなければなりません （MUST）。

[[WARC]] は、レコードの日時をその取り込みが始まった瞬間とし、1 つの取り込みの出来事の レコードに 1 つの日時を共有させます。交信にとってその瞬間は、ブラウザがリクエストを 始めたときです。producer がレコードを組み立てる時刻は、本文が届くのにかかった時間だけ 遅れ（大きな本文なら数分になります）、ページを取りに行った時刻ではなく producer が書いた 時刻を述べてしまいます。

既存の WARC の読み手は、response レコードの payload を HTTP/1.1 として 読みます。そのため HTTP/2 や HTTP/3 で運ばれた交信も HTTP/1.1 の形で書き、運んだ プロトコルの版は payload に残りません。

Payloads

ブラウザは文字の本文を、ほかの誰かが見る前に文字へ読み替え、道具には文字として渡します。 それをバイト列に書き戻すと、書き手が選んだ符号の本文になります —— 両者がたまたま一致 しない限り、オリジンが送った符号ではありません。この節の要件は、各レコードの payload を wire を渡ったバイト列に留め、payload digest がオリジンとブラウザの送ったものを保証する ようにします。

Response payloads

本文を持つ response レコードの payload は、サーバが送ったバイト列から Content-Encoding が名指す content-coding を外し、ほかは何も変えないもので なければなりません（MUST）。とくに producer は、文字の本文を ある文字符号から別の文字符号に変換してはなりません（MUST NOT）。 Shift_JIS で送られた本文はその Shift_JIS のバイト列のまま、media type が charset を 宣言しない本文は、ブラウザがどの charset で読んだかに関わらず、送られたとおりに保存します。

data: URL はどのサーバも送りません。その payload は URL が運ぶデータを、URL の 定めるとおり（base64、または percent-encoding をバイトとして）復号したもので、やはり変換 しません。

本文をバイト列として得られない producer は、文字から組み直した本文を保存しては なりません（MUST NOT）。そのレスポンスは、空の payload と、 truncated が not-intercepted の body not kept のレコードで記録します。

Request payloads

本文を持つ request レコードの payload は、ブラウザがリクエストの本文として 送ったバイト列でなければなりません（MUST）。それをバイト列として 得られない producer は、文字から組み直した本文を保存してはなりません （MUST NOT）。そのリクエストは本文なしで記録します。

Records of bodies not kept

サーバが送った本文を持たずに記録したレスポンスのそれぞれについて —— 送る本文を持たない レスポンス（HEAD リクエストへのもの、ステータス 1xx・204・ 3xx・304）を除いて —— response レコードを持つ ファイルは、metadata レコード —— 以下 body not kept のレコード —— も持たなければ なりません（MUST）。その WARC-Target-URI は レスポンスの URL で、WARC-Refers-To は response レコードの WARC-Record-ID でなければならず（MUST）、 application/warc-fields の本文は次を含まなければなりません （MUST）:

Field必須説明
truncatedはい レコードが本文を持たない理由。下の値のどれか。
encodedDataLengthいいえ レスポンス全体が wire を渡ったときの大きさ（バイト）。producer が知っている 場合に。
  • too-large —— 本文が、producer が 1 つの本文に置いた上限より大きかった。
  • task-cap —— 本文を残すと、取り込みが残した本文が、producer がその全体に 置いた上限を超えるところだった。
  • url-policy —— producer の URL の方針が、交信を本文なしで残すよう求めた。
  • content-type —— producer の media type の方針が、レスポンスの media type の本文を残さないよう求めた。
  • not-intercepted —— 本文は wire を渡ったが、producer がバイト列として 得られなかった（ を参照）。
WARC/1.1
WARC-Type: metadata
WARC-Target-URI: https://example.com/api/feed
WARC-Date: 2026-10-30T02:14:31.882Z
WARC-Refers-To: <urn:uuid:5c1f0b8e-2a77-4a5e-9d3e-0f6f3b1d2c4a>
Content-Type: application/warc-fields
Content-Length: 53

truncated: not-intercepted
encodedDataLength: 4821

サイズの上限で落とした本文（too-large と task-cap）の response レコードは WARC-Truncated: length を持ち （MUST）、取り込めなかった本文のものは WARC-Truncated: unspecified を持たなければなりません （MUST）。WARC ファイルだけを読む読み手が、空の payload を本文と 取り違えないようにするためです。

方針で省いた本文は途中で切ったものではないので、その response レコードは WARC-Truncated を持ちません。どの上限と方針が効いていたかは、WARC ファイルの 外、ファイルを収めるパッケージが記録します（[[BROWSERHIVE-WACZ-PROFILE]]）。

Records of withheld requests

producer が方針によって差し止めたリクエストのそれぞれについて、取り込みの WARC ファイルは metadata レコード —— 以下 withheld request のレコード —— を 含まなければなりません（MUST）。その WARC-Target-URI はリクエストの URL でなければならず （MUST）、application/warc-fields の本文は次を 含まなければなりません（MUST）:

Field必須説明
actionはい producer が何をしたか。deny: リクエストを送らなかった。その URL に ついて、取り込みを行う機械から出たものはありません。no-archive: リクエストを通し、オリジンは答えたが、この記録のほかには交信の何も残さなかった。 リクエストが送られたかどうかを述べるのはこの欄です。
patternはい 一致したパターン。producer の方針の綴りのとおりで、読み手がそちらで引き当て られるように。
methodはい リクエストのメソッド。
resourceTypeいいえ ページが何を取りに行っていたか。取り込みが知っている場合に。
targetいいえ 何がリクエストを出したか: page、iframe（browser が ページと別に走らせるフレーム。多くは別サイトのもの）、worker、 service_worker。取り込みが述べないときは置きません。
 
WARC/1.1
WARC-Type: metadata
WARC-Target-URI: https://www.example-analytics.com/collect?v=2
WARC-Date: 2026-09-06T02:14:31.882Z
Content-Type: application/warc-fields
Content-Length: 87

action: deny
pattern: *://*.example-analytics.com/*
method: POST
resourceType: XHR

deny は取り込みが起こすすべてのリクエストに届くので、そのレコードは、ページの どの部分がリクエストを出したかに関わらず書かなければなりません （MUST）。producer がほかには記録しない部分のリクエストも含みます。

withheld request のレコードはレスポンスも本文も持ちません。主張しているのは、ページがその URL を要求したこと、そして producer がそれについて何をするか決めたこと —— リクエストが 失敗したという意味でも、オリジンが何も返さなかったという意味でもありません。オリジンに 到達できなかった取り込みは、これをこの形で報告してはなりません （MUST NOT）。

交信を残して本文だけを残さない方針は、この種のレコードを生みません。request と response のレコードは通常どおり書かれ、欠けている本文は、truncated が url-policy の body not kept のレコードで報告されます —— 上限で 落としたものとしては報告されません。

Records of windows not opened

取り込みは 1 つのページを記録し、producer はページに新しい top-level browsing context —— ウィンドウやタブ —— を与えません（[[BROWSERHIVE-WACZ-PROFILE]]）。ページがそれを求めた 1 回ごとに、取り込みの WARC ファイルは metadata レコード —— 以下 window not opened のレコード —— を 含まなければなりません（MUST）。その WARC-Target-URI は、そのウィンドウが読み込むはずだった URL を browser が 知らせたとおりのものでなければなりません（MUST）: ページが名指し しなければ about:blank、form が求めたなら送る本文を除いた action の URL です。 application/warc-fields の本文は次を含まなければなりません （MUST）:

Field必須説明
windowはい not-opened。この版は、ほかの値を定めません。
windowNameいいえ ページがウィンドウに付けた名前。付けなければ _blank。ウィンドウを 名指ししない遷移（修飾キーつきの click など）で求めたときは置きません。
targetいいえ 何が求めたか: page、または iframe（browser がページと 別に走らせるフレーム。多くは別サイトのもの）。取り込みが述べないときは置きません。
 
WARC/1.1
WARC-Type: metadata
WARC-Target-URI: https://shop.example/campaign?from=top
WARC-Date: 2026-10-01T02:14:31.882Z
Content-Type: application/warc-fields
Content-Length: 54

window: not-opened
windowName: _blank
target: page

ウィンドウの文書のリクエストは送られていないので、その URL について、取り込みを行う機械から 出たものはありません。このレコードは、producer の URL の方針が URL に当たるかどうかに 関わらず書き、action を持ちません。これは withheld request のレコードではなく、読み手はそれとして数えてはなりません （MUST NOT）。

Snapshots

写しは、取り込みのある瞬間に、ページの主フレームの文書が どうなっていたかを写したものです。producer は写しを、そのときブラウザが持っている文書から —— スクリプトが変えたところは変わったまま —— 作り、サーバが送ったものからは作りません。 写しは、次のどれかの時点で取ります:

  • after-load —— ページが読み込まれて落ち着き、behavior がまだ 1 つも 走っていない。
  • after-behaviors —— 取り込みがページで走らせた behavior が終わった。

behavior は、取り込みがページ自身のもののほかにページで走らせるコードです。 たとえば検索の form に記入して送るものです。1 つの取り込みは各時点で写しを高々 1 つ取り、 behavior を走らせなかったときは after-behaviors では取りません。behavior の コード、取り込みがどの時点で写しを取ったか、ある時点で取らなかった理由は、ファイルを収める パッケージが記録します（[[BROWSERHIVE-WACZ-PROFILE]]）。

producer は写しを、一緒に書く 2 つのレコードで記録します: 写しを持つ resource レコードと、写しが何かを述べる metadata レコードです。2 つのレコードは WARC-Concurrent-To を持ってはなりません（MUST NOT）。 写しは交信の一部ではありません。[[WARC]] はその欄が結ぶレコードに 1 つの日時を 持たせますが、写しは、その文書を読み込んだ交信と日時を共有しません。

The resource record

写しの resource レコードは、写しを block として持ち、次のヘッダの欄を 持たなければなりません（MUST）:

Field必須説明
WARC-Target-URIはい urn:browserhive:snapshot: に続けて、時点、コロン、写しを取った 瞬間の文書の URL から fragment を除いたもの。たとえば urn:browserhive:snapshot:after-load:https://shop.example/。ページは History API で、別の文書を読み込まずに文書の URL を変えられるので、その URL は文書を 読み込んだ URL と同じとは限りません。
WARC-Dateはい producer が写しを取った瞬間。
Content-Typeはい text/html; charset=utf-8。
WARC-Block-Digestはい block の digest。
WARC-Payload-Digestはい payload の digest。resource レコードの payload は block そのもの なので [[WARC]]、同じバイト列から計算します。
 
WARC/1.1
WARC-Type: resource
WARC-Record-ID: <urn:uuid:d6874c5c-9710-40d4-9fb8-ceb24bb0dfc8>
WARC-Target-URI: urn:browserhive:snapshot:after-behaviors:https://shop.example/results
WARC-Date: 2026-11-02T01:20:07.415Z
Content-Type: text/html; charset=utf-8
WARC-Block-Digest: sha256:RK4XPNMRVNTPF7OWYGYRXMHDFC5H2RF7BH74Y2KKIRRELLG6MZJQ
WARC-Payload-Digest: sha256:RK4XPNMRVNTPF7OWYGYRXMHDFC5H2RF7BH74Y2KKIRRELLG6MZJQ
Content-Length: 237

<!DOCTYPE html>
<html lang="en"><head><base href="https://shop.example/results">
<meta charset="utf-8"><title>Results for lamp</title></head>
<body><form role="search"><input name="q" value="lamp"></form>
<h1>3 results</h1></body></html>

この例では、behavior がページで lamp を検索しました。ページは結果を表示し、別の 文書を読み込まずに URL を https://shop.example/ から変えました。behavior が 検索の欄に打ち込んだ値は、その欄の value 属性として写しに入っており、head の 先頭の base 要素は producer が入れたものです（ を参照）。

[[WARC]] は、resource レコードの http・https の target URI を、その URI に対して返されたもののためにとっておき、収集のほかの成果物には 合成した target URI を用意しています。写しはそうした成果物です。それ自身の URI の下に あれば、どの読み手も写しを、サーバが文書の URL に対して返したものと取らず、アーカイブした ページを配る読み手は、時刻がどうであれ、写しをその URL のレスポンスと取り違えません。

The metadata record

写しの metadata レコードは、写しが何かを述べます。その WARC-Refers-To は写しの resource レコードの WARC-Record-ID で、WARC-Target-URI と WARC-Date は そのレコードのものでなければならず（MUST）、 application/warc-fields の本文は次を含まなければなりません （MUST）:

Field必須説明
snapshotはい producer が写しを取った時点: after-load か after-behaviors。
document-uriはい 写しを取った瞬間の文書の URL を、ブラウザが持っていたとおりに。fragment も 含めます。
document-recordいいえ 文書を届けた response レコードの WARC-Record-ID （山括弧を含めて）。そのレコードは、取り込みの別のファイルにあってもかまいません。 取り込みがそのレコードを持たないときは置きません。
secrets-replacedはい producer が写しの中でシークレットの値を置き換えた回数を 10 進で （ を参照）。置き換えなかったときは 0。
 
WARC/1.1
WARC-Type: metadata
WARC-Target-URI: urn:browserhive:snapshot:after-behaviors:https://shop.example/results
WARC-Date: 2026-11-02T01:20:07.415Z
WARC-Refers-To: <urn:uuid:d6874c5c-9710-40d4-9fb8-ceb24bb0dfc8>
Content-Type: application/warc-fields
Content-Length: 158

snapshot: after-behaviors
document-uri: https://shop.example/results
document-record: <urn:uuid:3d6b2f0e-8c1a-4b7e-a2f4-6e9d1c5b8a07>
secrets-replaced: 0

この例の document-uri はページが変えた後の URL で、 document-record は、https://shop.example/ から文書を届けた response レコードを名指します。

本文は action・truncated・window を持ってはならず （MUST NOT）、読み手はこのレコードを withheld request のレコード・body not kept のレコード・ window not opened のレコードとして数えてはなりません （MUST NOT）。このレコードは WARC-Payload-Digest を 持ちません。[[WARC]] はその欄を、payload が定まっているレコードにしか認めていません。

What a snapshot holds

写しの resource レコードの block は、producer が文書を HTML に直列化し、 UTF-8 で符号化したものです。それは producer が作ったもので、サーバのものではなく、読み手は それをオリジンが送ったものと取ってはなりません（MUST NOT）。 オリジンがその文書について送ったものは、document-record が名指す response レコードにあります。

写しの head の最初の要素は、href 属性が、写しを取った瞬間の文書の base URL から fragment を除いたものである base 要素でなければなりません （MUST）。文書の base URL は、ページが相対 URL を解決した URL で、 ページが自分の base 要素で別のものを定めていなければ、文書の URL です。読み手は 写しを写し自身の URI の下で配るので、この要素によって、写しの中の相対 URL がページの中と 同じに解決します。

写しは、ページのスクリプトを含んではなりません（MUST NOT）。 すなわち、どの名前空間の script 要素も、名前が on で始まる属性も、 それらを持ちうる文書を運ぶ srcdoc 属性も持たず、href・ xlink:href・src・action・formaction・ data の属性に、javascript:void(0) のほかの javascript: の URL を持ちません。

写しの中で、type が password の input 要素は、 その欄が何を持っていたかに関わらず、value 属性を持ってはなりません （MUST NOT）。

シークレットは、取り込みを求めた側が、behavior に読ませるために 秘密として渡した値です（[[BROWSERHIVE-WACZ-PROFILE]]）。写しは、シークレットの値を、 そのままの形でも、HTML の直列化が文字を escape した形（たとえば & を &amp; とした形）でも、含んではなりません（MUST NOT）。 producer は現れたところをそれぞれ置き換え、置き換えた回数を secrets-replaced に数えます。

Making a snapshot

producer は、次のようにして、これらの要件を満たし、写しをページが表示していたものに 近く保てます:

  • 文書を、producer 自身のスクリプトの文脈（Chromium では isolated world）から読みます。 そこでは、ページのスクリプトが文書の読み方を変えられません。
  • 文書を複製し、ページがマークアップの外に持っているものを複製に書き込みます: 各欄の いまの値を value 属性として（textarea では中身として）、 どの box に check が入り、どの option が選ばれているか、開いた shadow root を shadowrootmode 属性つきの template 要素として、ページが adopt した style sheet を style 要素として、各 canvas を それが表示していた画像として。ページが画素を読めなかった canvas は空のまま、 パスワードの欄は値を持ちません。
  • script と noscript の要素、スクリプトを先読みする link 要素（rel="modulepreload"、または as="script" の rel="preload"）を取り除きます。event handler の属性と srcdoc を取り除き、javascript: の URL を javascript:void(0) に置き換えます。リンクはリンクの見た目のまま 残ります。
  • フレームの src はそのままにします。フレームの文書は写しに含まれず、 読み手は、取り込みがその URL について記録したものを表示します。
  • 文書の doctype を、無かったなら無いまま、もとのとおりに残します。読み手が写しを ページと同じモードで描くようにするためです。
  • 複製の head の先頭に、ページが使っていた文書の base URL を持つ base 要素を置きます。
  • 複製を直列化し、その結果の中のシークレットを、そのままの形と escape した形のどちらも *** に置き換えます。

Security and privacy considerations

WARC ファイルは wire を渡ったものを持ちます。request レコードはブラウザが 送ったヘッダの欄を持ち、そこには cookie や認証の情報が含まれることがあります。 response レコードはオリジンが返したものを、その中の個人の情報も含めて 持ちます。

withheld request のレコードは一度も送られなかったリクエストの URL を、 window not opened のレコードは一度も読み込まれなかった文書の URL を持ちます。 どちらの URL も、クエリ文字列に識別子を運んでいることがあります。リクエストを差し止めると オリジンには届きませんが、その URL はファイルに残ります。

写しは、そのときのページの文字を持ち、ページのスクリプトと取り込みの behavior が欄に入れたものも持ちます: パスワードの欄を除き、どの欄の値も写しに 入ります。producer は、そこに見つけたシークレットの値を、そのままの形でも HTML の escape の形でも置き換えますが、ページが変換したシークレット（たとえば URL に符号化した もの）や、誰もシークレットと告げなかったものは見つけません。写しの document-uri は文書の URL の fragment を残します。fragment はサーバに送られる ことがなく、ログインの手順によっては、ページにトークンを渡すのに使われます。

ファイルを人に渡す者は、これらをすべて渡します。写しが除くものを除けば、本仕様は producer に そのどれかを取り除くことを求めません。取り込みが何をレコードに残さないかは取り込みの方針が決め、方針は ファイルを収めるパッケージが記録します（[[BROWSERHIVE-WACZ-PROFILE]]）。
