本仕様は [[WARC]] のプロファイルです。BrowserHive が WARC ファイルにどのレコードを書き、 それぞれが何を持つかを定めます。ファイルだけを手にした読み手が、その取り込みが何を記録し、 何を残さず、それがなぜかを判断できるようにするためです。

これは作業中の草案です。BrowserHive が現在書き出しているものを記述しています。同プロジェクト 以外での位置づけを持たず、[[WARC]] の発行者から承認されたものでもありません。

BrowserHive が書く WARC のレコードの決まりは、[[BROWSERHIVE-WACZ-PROFILE]] の 1.15.0 までは、その中にありました。ここへ移したのは、WARC ファイルが自分の従う決まりを自分で 名乗れるようにするため（ を参照）、そしてパッケージから取り出して 読んだファイルも同じ意味を保つようにするためです。BrowserHive WACZ Profile 1.27.0 は、 パッケージの WARC ファイルがこの版に適合することを求めます。

[[WARC]] は WARC-Profile というヘッダの欄を定めており、それは revisit レコードの読み方を述べます。本仕様は、その欄とは関係がありません。

Introduction

[[WARC]] は、レコードの枠の作り方と、レコードが持つヘッダの欄を定めます。payload に何を 入れるか、残さなかった本文や送らなかったリクエストについてどのレコードを書くか、そしてその 理由をどう述べるかは、書き手に委ねています。BrowserHive WARC ファイルの読み手にはその答えが 要り、それはファイルを書いている間にしか知りえません。

本プロファイルはそれを定めます。[[WARC]] の求めることは何も変えません。 redacted のレコードは [[WARC]] が勧めるものより少なく持ちますが、そのことを自分の欄で 名乗ります（Conformance を参照）。本プロファイルが 足すレコードの多くは metadata レコードで、本プロファイルを知らない読み手は 読み飛ばせます。写しは、それ自身の URI の下で resource レコードでも 記録し、そのレコードはそうした読み手のためのものです: アーカイブしたページを配る読み手は、 それを一覧に載せて手持ちのページと同じように配り、写しを取ったときのページの姿を見せます。 フレームの写し（ページのフレームの 1 つの文書の写し）も同じ形で、それ自身の URI の下に 記録し、そのフレームを持つ写しがその URI を名指します。その名指しを知る読み手は、フレームも そのときの姿で見せられます。 スクリーンショットも同じ形で記録します: その resource レコードは画像を 持ち、そうした読み手は、それをスクリーンショット自身の URI の下で見せられます。

BrowserHive は WARC ファイルを WACZ パッケージに書き込み、パッケージの決まりは [[BROWSERHIVE-WACZ-PROFILE]] にあります。ここで定めるのは 1 本の WARC ファイルが持つ ものだけです。パッケージから取り出したファイルにも、そのまま当てはまるようにするためです。

Conformance

本仕様の適合対象は WARC ファイル、すなわちファイル 1 つです。適合はファイルの性質であって、 それを書くソフトウェアの性質ではありません。

適合するファイルは、適合する [[WARC]] ファイルです。本仕様は要求を追加します。 [[WARC]] の要求を取り除くことも、緩めることもしません。本仕様のいずれかの版に適合する WARC ファイルを BrowserHive WARC ファイルと呼びます。それ以外の WARC ファイルが何を持つかに ついて、本仕様は何も求めません。

本仕様が [[WARC]] から外れる所は、どれも [[WARC]] が勧めること・述べることからであって、 求めることからではなく、そのレコードを定める節がそう述べます。たとえば、交信の payload は content-coding を外した本文を HTTP/1.1 の形で書いたもので（ を参照）、 redacted のレコードは [[WARC]] が勧めるものより少なく持ち、そのことを自分の BrowserHive-Redacted の欄で名乗ります。 [[WARC]] は、request レコードの block が the full HTTP request sent over the network を、response レコードの block が the full HTTP response received over the network を持つことを勧めていますが、 redacted のレコードは、そのメッセージを値を置き換えた形で持ちます。 [[WARC]] は WARC-Target-URI を the original URI としていますが、 redacted のレコードでは、URI の値を置き換えたほかのレコードと同じく （ を参照）、その URI の値を置き換えた形です。

本仕様における MUST（〜しなければならない）、 MUST NOT（〜してはならない）、 SHOULD（〜すべきである）、 MAY（〜してもよい）は、[[RFC2119]] の記述どおりに解釈します。

producer は、ファイルを書くソフトウェアです。取り込みは、1 つの ページに対する producer の 1 回の実行です。1 つの取り込みは、1 本以上の WARC ファイルを 書きます。

The warcinfo record

各 WARC ファイルは、WARC-Filename がそのファイル自身の名前である warcinfo レコードで始まらなければなりません（MUST）。 その application/warc-fields の本文は、下の表で必須とした欄を含まなければ なりません（MUST）。

Field必須説明
conformsToはい そのファイルが満たすと主張する本仕様の版の URL。この版では https://uraitakahito.github.io/browserhive-warc-spec/1.5.0/。この欄は ちょうど 1 回現れなければなりません（MUST）。
formatはい WARC File Format 1.1。
softwareはい producer とその版。
robots-policyいいえ ignore: producer は robots.txt を見ません。ページを そもそも取り込むかどうかは、取り込みを求める側が決めることです。
descriptionいいえ 何を取り込んだかを述べる自由な文。
 
WARC/1.1
WARC-Type: warcinfo
WARC-Record-ID: <urn:uuid:0b7e8a52-6a63-4f0e-9d0b-6f1c2a3e4d5f>
WARC-Date: 2026-11-01T02:14:31.882Z
WARC-Filename: data-000.browserhive.warc.gz
Content-Type: application/warc-fields
Content-Length: 203

software: browserhive/31.2.0
format: WARC File Format 1.1
conformsTo: https://uraitakahito.github.io/browserhive-warc-spec/1.5.0/
robots-policy: ignore
description: Capture of https://shop.example/

conformsTo が名指すのは本プロファイルで、[[WARC]] ではありません。基底の形式は format が名指し、適合するファイルはどれも WARC 1.1 のファイルです （Conformance を参照）。名乗りが 1 つなら、読み手はどちらを取るか迷いません。読み手は、 conformsTo 以外の何かから、本仕様のある版への適合を推し量ってはなりません （MUST NOT）。とりわけ、ファイルの名前から推し量ってはなりません。 パッケージの決まりがファイルに付ける名前の印（data-000.browserhive.warc.gz。 [[BROWSERHIVE-WACZ-PROFILE]] を参照）は手がかりで、適合しないファイルも同じ名前を持ちえます。

Records and files

1 つのレコードが 2 つのファイルにまたがってはなりません（MUST NOT）。 レコードは 1 つのファイルに丸ごと書かれ、producer は continuation レコードを 書きません。1 つの交信のレコードは、同じファイルに在らなければならず （MUST）、1 つの写しの 2 つのレコードも、1 つの フレームの写しの 2 つのレコードも、1 つの スクリーンショットの 2 つのレコードも同じです（MUST）。

1 つの取り込みが、2 本以上のファイルを書くことがあります。それらのファイルの名前と、 producer がいつ新しいファイルを始めるかは、ファイルを収めるパッケージの決まりで、1 本の ファイルの決まりではありません。[[BROWSERHIVE-WACZ-PROFILE]] を参照してください。

Exchanges

交信は、ブラウザが送った 1 つのリクエストと、それに対して受け取った レスポンスです。producer は交信を request レコードと response レコードで記録し、レスポンスを本文なしで記録したときは、さらに body not kept のレコードを書きます。request レコードと response レコードは、WARC-Concurrent-To で互いを名指さなければ なりません（MUST）。

1 つの交信のレコードは、同じ WARC-Date を持たなければなりません （MUST）。その値は、ブラウザがリクエストを始めた時刻で、ブラウザが 知らせたとおりのものです。redirect するレスポンスは、その交信を終えます。redirect の後に 続くリクエストは、自分の時刻を持つ別の交信を始めます。

response レコードの payload は、交信を運んだプロトコルの版に関わらず、 HTTP/1.1 の形 [[RFC9112]]（ステータス行、ヘッダの欄、本文の順）でなければなりません （MUST）。

[[WARC]] は、レコードの日時をその取り込みが始まった瞬間とし、1 つの取り込みの出来事の レコードに 1 つの日時を共有させます。交信にとってその瞬間は、ブラウザがリクエストを 始めたときです。producer がレコードを組み立てる時刻は、本文が届くのにかかった時間だけ 遅れ（大きな本文なら数分になります）、ページを取りに行った時刻ではなく producer が書いた 時刻を述べてしまいます。

既存の WARC の読み手は、response レコードの payload を HTTP/1.1 として 読みます。そのため HTTP/2 や HTTP/3 で運ばれた交信も HTTP/1.1 の形で書き、運んだ プロトコルの版は payload に残りません。

Payloads

ブラウザは文字の本文を、ほかの誰かが見る前に文字へ読み替え、道具には文字として渡します。 それをバイト列に書き戻すと、書き手が選んだ符号の本文になります —— 両者がたまたま一致 しない限り、オリジンが送った符号ではありません。この節の要件は、各レコードの payload を wire を渡ったバイト列に留め、payload digest がオリジンとブラウザの送ったものを保証する ようにします。例外は、BrowserHive-Redacted の欄が payload を挙げる redacted のレコードです。その payload の中の値は置き換えてあり、その payload digest が 保証するのは、レコードが持つバイト列だけです。

Response payloads

本文を持つ response レコードの payload は、サーバが送ったバイト列から Content-Encoding が名指す content-coding を外し、redacted のレコードが 置き換えるもの（ を参照）のほかは何も変えないもので なければなりません（MUST）。とくに producer は、文字の本文を ある文字符号から別の文字符号に変換してはなりません（MUST NOT）。 Shift_JIS で送られた本文はその Shift_JIS のバイト列のまま、media type が charset を 宣言しない本文は、ブラウザがどの charset で読んだかに関わらず、送られたとおりに保存します。

data: URL はどのサーバも送りません。その payload は URL が運ぶデータを、URL の 定めるとおり（base64、または percent-encoding をバイトとして）復号したもので、やはり変換 しません。redacted のレコードが置き換えるものは、同じく例外です。

本文をバイト列として得られない producer は、文字から組み直した本文を保存しては なりません（MUST NOT）。そのレスポンスは、空の payload と、 truncated が not-intercepted の body not kept のレコードで記録します。

Request payloads

本文を持つ request レコードの payload は、redacted のレコードが置き換える もの（ を参照）を除き、ブラウザがリクエストの本文として 送ったバイト列でなければなりません（MUST）。それをバイト列として 得られない producer は、文字から組み直した本文を保存してはなりません （MUST NOT）。そのリクエストは本文なしで記録します。

Redacted records

シークレットは、取り込みを求めた側が、 behavior に読ませるために秘密として渡した値です。 隠すシークレットは、 取り込みを求めた側が残すことを求めなかったシークレットです。その値は少なくとも 8 文字です（UTF-16 の code unit で数えます）: producer は、それより短い値を、残すことを求めずに渡す要求を断ります。 取り込みがどのシークレットを渡され、そのどれを残したかは、 ファイルを収めるパッケージの settings に記録します （[[BROWSERHIVE-WACZ-PROFILE]]）。

各 request レコードと response レコードで、producer は、 隠すシークレットの値の出現を、 WARC-Target-URI、リクエスト行、HTTP のヘッダの欄の値、文字の本文の中で、 3 文字の *** に置き換えなければなりません（MUST）。 1 つでも置き換えたレコードが redacted のレコードです。 ある出現が別の出現を含むときは、producer は長いほうを置き換え、 書いた *** の 1 つを 1 回の置き換えとします。

出現は、producer が認識する値の形です: 値そのまま（UTF-8）と、次の綴りです。

  • encodeURIComponent が符号化した形、 application/x-www-form-urlencoded の本文が符号化した形、 URL の path や query が符号化した形の percent-encoding（16 進の数字は大文字でも小文字でも）。
  • JSON の文字列の中で、JSON が求める escape だけを使った形。
  • HTML の中で、文字を &amp;・&lt;・ &gt;・&quot;・&nbsp; にした形と、 アポストロフィを &#39;・&#x27;・ &apos; のどれかにした形。
  • 値だけを base64 にした形。
  • Authorization・Proxy-Authorization のヘッダの欄の値の中で、 HTTP の Basic 認証の、符号化した認証情報の全体。復号すると値を持つものです。
  • base64 の data: URL のデータの全体。復号すると値を持つものです。
  • ヘッダの欄の値の中で、上のどれかの UTF-8 の 1 バイトずつを Latin-1 の 1 文字に読んだ形。 UTF-8 で届いた欄をブラウザが報告するときの形です。

producer は、ファイルのほかのどこにも出現を書いてはなりません （MUST NOT）。 ほかのレコードの WARC-Target-URI でも、同じように出現を置き換えます。

WARC-Target-URI は URI のままにします。[[WARC]] が URI を求めており、 URI には scheme が要るからです。値が scheme から始まるときなど、置き換えると URI の scheme が無くなるときは、producer は結果の前に元の scheme とコロンを書かなければなりません （MUST）。値が https://shop.example/a のとき、 URI の https://shop.example/a?b=c は https:***?b=c になります。 それでも URI にならないとき（値が port の中から始まるときなど）は、scheme とコロンと *** だけを書かなければなりません（MUST）。

出現を持つリクエストへのレスポンスは、シークレットの代わりになる cookie を設定することが あります。producer がそのようなレスポンスを見て、その Set-Cookie のヘッダの欄が、 値の長さが 8 文字以上の cookie を設定しているとき、producer はその値を、 そのレスポンスが届いた瞬間から、隠すシークレットの値として扱わなければなりません （MUST）。そのレスポンスのレコードでも、この決まりでも同じです。

redacted のレコードは、producer がどこで値を何回置き換えたかを述べる BrowserHive-Redacted の欄を、WARC のレコードのヘッダに持たなければなりません （MUST）: 

BrowserHive-Redacted: target-uri=1, headers=1, payload=2

この欄は、producer が 1 つ以上の出現を置き換えた場所のそれぞれについて 1 つの part を、 次の表の順に持ち、ほかの場所の part を持ちません:

Part数えるもの
target-uri WARC-Target-URI の中の置き換え。 リクエスト行は同じ出現を繰り返すだけで、もう一度は数えません。
headers HTTP のヘッダの欄の値の中の置き換え。
payload 本文の中の置き換え。
 
BrowserHive-Redacted = "BrowserHive-Redacted" ":" redacted-part *( "," SP redacted-part )
redacted-part        = part-name "=" part-count
part-name            = "target-uri" | "headers" | "payload"
part-count           = 1*DIGIT   ; 10 進。1 以上で、先頭に 0 を付けない

[[WARC]] はこの種の欄を認めています: その File and record model の節は、 拡張が新しい named field を定めることを認め、Named fields の節の General は、 認識できない名前の欄をソフトウェアに無視させます。 この欄の無い request レコードと response レコードは、 値を置き換えていてはなりません（MUST NOT）。 それらは、本仕様の残りが述べるとおりのものを持ちます。 ほかの型のレコードは、WARC-Target-URI の値を置き換えていても、 この欄を持ってはなりません（MUST NOT）。 読み手は、そこの *** と URL の中の同じ字とを区別できません。

次の redacted の request レコードの抜粋では、隠すシークレットの値が、 クエリ、ヘッダの欄 1 つ、ページが送った form の 2 か所にありました: 

WARC-Type: request
WARC-Target-URI: https://shop.example/login?key=***
Content-Type: application/http;msgtype=request
BrowserHive-Redacted: target-uri=1, headers=1, payload=2

POST /login?key=*** HTTP/1.1
Host: shop.example
Content-Type: application/x-www-form-urlencoded
Content-Length: 32
X-Api-Key: ***

user=alice&password=***&note=***

この節の決まりでは、文字の本文は、media type が次のどれかである 本文です。レスポンスの本文の media type はブラウザが判定したもの、 リクエストの本文の media type は Content-Type のヘッダの欄が宣言するものです。

  • text/*。
  • JSON: application/json と、+json で終わる型。
  • XML: application/xml、application/xhtml+xml と、+xml で終わる型。
  • JavaScript: application/javascript・ application/ecmascript・application/x-javascript・ application/x-ecmascript。
  • application/x-www-form-urlencoded。

文字の本文でない本文が出現を持つとき、 producer はその中を置き換えてはなりません（MUST NOT）。 長さが変わると本文が壊れるためです。 producer はそのメッセージを、その本文なしで記録し、 レコードは WARC-Truncated: secret を持たなければなりません （MUST）。 [[WARC]] の WARC-Truncated の節は、拡張がほかの理由を定めることを認めています。 このように記録した response は、 truncated が secret の body not kept のレコードも持ちます。 そのレコードが述べるのはレスポンスだけなので、 request は WARC-Truncated: secret だけを持ちます。 本文を落としても何も置き換えたことにはならないので、 BrowserHive-Redacted のどの part にも数えません。 ほかに何も置き換えなかったレコードは、WARC-Truncated を持ち、 BrowserHive-Redacted を持ちません。 

WARC/1.1
WARC-Type: metadata
WARC-Record-ID: <urn:uuid:a41d7e20-9b3c-4f15-8e62-5c0a7d3b1f94>
WARC-Target-URI: https://shop.example/export?key=***
WARC-Date: 2026-11-07T02:14:31.882Z
WARC-Refers-To: <urn:uuid:7c2e4b19-3f6a-4d08-8a51-2b9d0e6f1c37>
Content-Type: application/warc-fields
Content-Length: 44

truncated: secret
encodedDataLength: 4821

redacted のレコードと、producer が本文を落としたレコードの Content-Length・WARC-Block-Digest・WARC-Payload-Digest と、 その HTTP のメッセージが持つ Content-Length のヘッダの欄は、 レコードが持っているバイト列を述べなければなりません（MUST）。 producer は、どちらの digest の欄にも、置き換える前のバイト列や落とした本文の digest を 書いてはなりません（MUST NOT）。 レコードが持っているバイト列と合わせると、読み手が値の候補を試せてしまうためです。

シークレットから作った値（ハッシュや暗号文など）は出現ではなく、 オリジンがレスポンスの本文で新しく発行した資格（JSON の token など）も出現ではありません。 本仕様は、ファイルがそれらを持たないとは主張しません。

Records of bodies not kept

サーバが送った本文を持たずに記録したレスポンスのそれぞれについて —— 送る本文を持たない レスポンス（HEAD リクエストへのもの、ステータス 1xx・204・ 3xx・304）を除いて —— response レコードを持つ ファイルは、metadata レコード —— 以下 body not kept のレコード —— も持たなければ なりません（MUST）。その WARC-Target-URI は レスポンスの URL で（隠すシークレットの値は置き換えた形。 を参照）、WARC-Refers-To は response レコードの WARC-Record-ID でなければならず（MUST）、 application/warc-fields の本文は次を含まなければなりません （MUST）:

Field必須説明
truncatedはい レコードが本文を持たない理由。下の値のどれか。
encodedDataLengthいいえ レスポンス全体が wire を渡ったときの大きさ（バイト）。producer が知っている 場合に。
  • too-large —— 本文が、producer が 1 つの本文に置いた上限より大きかった。
  • task-cap —— 本文を残すと、取り込みが残した本文が、producer がその全体に 置いた上限を超えるところだった。
  • url-policy —— producer の URL の方針が、交信を本文なしで残すよう求めた。
  • content-type —— producer の media type の方針が、レスポンスの media type の本文を残さないよう求めた。
  • not-intercepted —— 本文は wire を渡ったが、producer がバイト列として 得られなかった（ を参照）。
  • secret —— 本文が文字の本文でなく、隠すシークレットの値を 持っていた（ を参照）。

サイズの上限で落とした本文（too-large と task-cap）の response レコードは WARC-Truncated: length を持ち （MUST）、取り込めなかった本文のものは WARC-Truncated: unspecified を持ち（MUST）、 隠すシークレットの値を持っていて落とした本文（secret）のものは WARC-Truncated: secret を持たなければなりません （MUST）。WARC ファイルだけを読む読み手が、空の payload を本文と 取り違えないようにするためです。

Records of withheld requests

producer が方針によって差し止めたリクエストのそれぞれについて、取り込みの WARC ファイルは metadata レコード —— 以下 withheld request のレコード —— を 含まなければなりません（MUST）。その WARC-Target-URI はリクエストの URL（隠すシークレットの値は置き換えた形。 を参照）でなければならず （MUST）、application/warc-fields の本文は次を 含まなければなりません（MUST）:

Field必須説明
actionはい producer が何をしたか。deny: リクエストを送らなかった。その URL に ついて、取り込みを行う機械から出たものはありません。no-archive: リクエストを通し、この記録のほかには交信の何も残さなかった。 リクエストが送られたかどうかを述べるのはこの欄です。
patternはい 一致したパターン。producer の方針の綴りのとおりで、読み手がそちらで引き当て られるように。
methodはい リクエストのメソッド。
resourceTypeいいえ ページが何を取りに行っていたか。取り込みが知っている場合に。
targetいいえ 何がリクエストを出したか: page、iframe（browser が ページと別に走らせるフレーム。多くは別サイトのもの）、worker、 service_worker。取り込みが述べないときは置きません。

WARC-Target-URI: https://www.example-analytics.com/collect?v=2
WARC-Date: 2026-09-06T02:14:31.882Z
Content-Type: application/warc-fields
Content-Length: 87

action: deny
pattern: *://*.example-analytics.com/*
method: POST
resourceType: XHR

deny は取り込みが起こすすべてのリクエストに届くので、そのレコードは、ページの どの部分がリクエストを出したかに関わらず書かなければなりません （MUST）。producer がほかには記録しない部分のリクエストも含みます。

withheld request のレコードはレスポンスも本文も持ちません。主張しているのは、ページがその URL を要求したこと、そして producer がそれについて何をするか決めたこと —— リクエストが 失敗したという意味でも、オリジンが何も返さなかったという意味でもありません。オリジンに 到達できなかった取り込みは、これをこの形で報告してはなりません （MUST NOT）。

交信を残して本文だけを残さない方針は、この種のレコードを生みません。request と response のレコードは通常どおり書かれ、欠けている本文は、truncated が url-policy の body not kept のレコードで報告されます —— 上限で 落としたものとしては報告されません。

Records of windows not opened

取り込みは 1 つのページを記録し、producer はページに新しい top-level browsing context —— ウィンドウやタブ —— を与えません（[[BROWSERHIVE-WACZ-PROFILE]]）。ページがそれを求めた 1 回ごとに、取り込みの WARC ファイルは metadata レコード —— 以下 window not opened のレコード —— を 含まなければなりません（MUST）。その WARC-Target-URI は、そのウィンドウが読み込むはずだった URL を browser が 知らせたとおりのもの（隠すシークレットの値は置き換えた形。 を参照）でなければなりません （MUST）: ページが名指し しなければ about:blank、form が求めたなら送る本文を除いた action の URL です。 application/warc-fields の本文は次を含まなければなりません （MUST）:

Field必須説明
windowはい not-opened。この版は、ほかの値を定めません。
windowNameいいえ ページがウィンドウに付けた名前。付けなければ _blank。ウィンドウを 名指ししない遷移（修飾キーつきの click など）で求めたときは置きません。
targetいいえ 何が求めたか: page、または iframe（browser がページと 別に走らせるフレーム。多くは別サイトのもの）。取り込みが述べないときは置きません。

WARC-Target-URI: https://shop.example/campaign?from=top
WARC-Date: 2026-10-01T02:14:31.882Z
Content-Type: application/warc-fields
Content-Length: 54

window: not-opened
windowName: _blank
target: page

ウィンドウの文書のリクエストは送られていないので、その URL について、取り込みを行う機械から 出たものはありません。このレコードは、producer の URL の方針が URL に当たるかどうかに 関わらず書き、action を持ちません。これは withheld request のレコードではなく、読み手はそれとして数えてはなりません （MUST NOT）。

Snapshots

写しは、取り込みのある瞬間に、ページの主フレームの文書が どうなっていたかを写したものです。producer は写しを、そのときブラウザが持っている文書から —— スクリプトが変えたところは変わったまま —— 作り、サーバが送ったものからは作りません。 写しは、次のどれかの時点で取ります:

  • after-load —— ページが読み込まれて落ち着き、behavior がまだ 1 つも 走っていない。
  • after-behaviors —— 取り込みがページで走らせた behavior が終わった。

behavior は、取り込みがページ自身のもののほかにページで走らせるコードです。 たとえば検索の form に記入して送るものです。1 つの取り込みは各時点で写しを高々 1 つ取り、 behavior を走らせなかったときは after-behaviors では取りません。ある時点の写しと 一緒に、producer はページのフレームのうち読める文書を写します（ を参照）。behavior の コード、取り込みがどの時点で写しを取ったか、ある時点で取らなかった理由、どのフレームを写したかは、 ファイルを収めるパッケージが記録します（[[BROWSERHIVE-WACZ-PROFILE]]）。

producer は写しを、一緒に書く 2 つのレコードで記録します: 写しを持つ resource レコードと、写しが何かを述べる metadata レコードです。2 つのレコードは WARC-Concurrent-To を持ってはなりません（MUST NOT）。 写しは交信の一部ではありません。[[WARC]] はその欄が結ぶレコードに 1 つの日時を 持たせますが、写しは、その文書を読み込んだ交信と日時を共有しません。

What a snapshot holds

写しの resource レコードの block は、producer が文書を HTML に直列化し、 UTF-8 で符号化したものです。それは producer が作ったもので、サーバのものではなく、読み手は それをオリジンが送ったものと取ってはなりません（MUST NOT）。 オリジンがその文書について送ったものは、document-record が名指す response レコードにあります（そこで隠すシークレットのために producer が 置き換えたものや落としたものを除きます）。

写しの head の最初の要素は、href 属性が、写しを取った瞬間の文書の base URL から fragment を除いたものである base 要素でなければなりません （MUST）。文書の base URL は、ページが相対 URL を解決した URL で、 ページが自分の base 要素で別のものを定めていなければ、文書の URL です。読み手は 写しを写し自身の URI の下で配るので、この要素によって、写しの中の相対 URL がページの中と 同じに解決します。

写しは、ページのスクリプトを含んではなりません（MUST NOT）。 すなわち、どの名前空間の script 要素も、名前が on で始まる属性も、 それらを持ちうる文書を運ぶ srcdoc 属性も持たず、href・ xlink:href・src・action・formaction・ data の属性に、javascript:void(0) のほかの javascript: の URL を持ちません。

写しの中で、type が password の input 要素は、 その欄が何を持っていたかに関わらず、value 属性を持ってはなりません （MUST NOT）。

写しは、シークレットの値を、隠すものかどうかに関わらず、 そのままの形でも、HTML の直列化が文字を escape した形（たとえば & を &amp; とした形）でも、含んではなりません（MUST NOT）。 producer は、base 要素の href でも写しのほかのところでも、 現れたところをそれぞれ置き換え、置き換えた回数を secrets-replaced に数えます。

Frame snapshots

フレームの写しは、ページのフレームの 1 つの文書を、 写しの時点で写したものです。producer はフレームの写しを、ある時点の写しと一緒にだけ 取ります。写しを取らない時点では、フレームの写しも取りません。

フレームは主フレームの文書から辿ります。producer はその文書の要素を木の順に進み、出会った frame・iframe の要素のうち文書を持つものは、それぞれ次のどれかです:

  • 文書が別の origin のもので、producer が主フレームからその文書を読めないフレーム。 producer はそれを写さず、中へも入りません。
  • 文書を読めて、その URL の scheme が http でも https でもない フレーム。たとえば about:blank、srcdoc 属性の about:srcdoc、data: の URL です。producer はそれを写さず、 中へも入りません。
  • 文書を読めて、その URL の scheme が http か https である フレーム。以下、番号を付けるフレームと呼びます。 producer はそれに 1 から数えて次の番号を付け、その文書の要素を同じように進んでから、 そのフレームの要素の後に続く要素へ進みます。

したがって番号は要素の順に従い、フレームはその文書の中のフレームより先で、深さ優先です。 入れ子の文書のフレームも、主フレームの文書のフレームと同じように番号を付けます。番号は 1 つの時点のものです: フレームには時点ごとに改めて番号を付け、2 つの時点の同じ番号が同じ フレームとは限りません。

producer は、番号を付けるフレームでないフレームのフレームの写しを取ってはならず （MUST NOT）、番号を付けるフレームのそれぞれについて、1 つの時点で 高々 1 つ取ります。取り込みの方針がその文書を伏せる（ページから読むものに入れない）番号を 付けるフレームについても、そうしたフレームの文書の中やさらにその下の番号を付けるフレームに ついても、取ってはなりません（MUST NOT）。どの方針が文書を伏せるか、取り込みが ある時点でどの番号を付けるフレームを写したか、写さなかったものがなぜかは、ファイルを収める パッケージが記録します（[[BROWSERHIVE-WACZ-PROFILE]]）。producer は、写しの大きさなど 自分の理由で、番号を付けるフレームを写さないこともあります。

フレームの写しは、主フレームの文書の代わりにフレームの文書を置いて、写しと同じように記録し、 写しと同じものを持ちます。producer はそれを、一緒に書く resource レコードと metadata レコードで記録し、2 つは WARC-Concurrent-To を持っては なりません（MUST NOT）。・ ・ が写しについて 述べることは、レコードの URI と が足す欄を除き、 フレームの写しにも当てはまります。したがって写しの head の最初の要素は、フレームの文書の base URL を持つ base 要素で、写しはその文書のスクリプトを 1 つも持たず、 シークレットの値はその中で置き換えます。

producer はページを、主フレームの中の自分のスクリプトの文脈から読みます。ブラウザは、 フレームの文書をスクリプトに読ませるのを、両者が同じ origin のときに限ります。別のサイトの 文書は、ページ自身のスクリプトの手が届かないのと同じく、producer の手も届きません。 http・https の URL を持たない文書は、読み手が引ける URL から 読み込んだものではなく、その中のフレームを名指せる写しもありません。

フレームの写しの 2 つのレコードは食い違いません。snapshot の値は WARC-Target-URI の中の時点で、frame の値はその中の番号で、その中の URL は document-uri から fragment を除いたものでなければなりません （MUST）。WARC-Target-URI が urn:browserhive:frame-snapshot: で始まる resource レコードの それぞれについて、それを WARC-Refers-To で名指す、この節が述べる metadata レコードが、ちょうど 1 つ在らなければなりません （MUST）。1 つの時点の 2 つのフレームの写しが、同じ番号を持っては なりません（MUST NOT）。

Naming a frame snapshot from its parent

写しとフレームの写しの中で、producer が同じ時点でフレームの写しを取ったフレームの要素は、 値がそのフレームの写しの resource レコードの WARC-Target-URI である data-browserhive-snapshot 属性を持たなければならず、その src 属性は ページの中のとおりでなければなりません（MUST）。ほかの要素は、 この属性を持ってはなりません（MUST NOT）: producer がフレームの写しを 取らなかったフレームの要素も、ページの中でこの属性を持っていた要素も持たず、後者からは producer が属性を取り除きます。属性の値の中のシークレットの値は、URI と同じく 置き換えた形で、その置き換えは secrets-replaced に数えません。

フレームの写しを名指す写しは、その親の写しです: parent が 0 なら その時点の写し、そうでなければ、その時点のフレームの写しのうち frame が parent であるもの。producer が親を写さなかったときは、どの属性もそのフレームの 写しを名指しません。

この属性を知らない読み手は、写しのフレームの中に、取り込みが src の URL について 記録したものを、手持ちのページと同じように見せます。この属性を知る読み手は、代わりに、属性が 名指すフレームの写しをそのフレームの中に見せてもかまいません（MAY）。 それは、写しの時点のフレームの姿を見せます。

取り込みがフレームの URL について記録したのは、サーバが送ったとおりの文書で、ページの スクリプトがその後で変えたかもしれないものです。src をそのままにすれば、 本プロファイルを知らない読み手は、この版より前と同じくその文書を見せ、属性はそれを探す読み手に 写しを差し出します。

Making a snapshot

producer は、次のようにして、これらの要件を満たし、写しをページが表示していたものに 近く保てます:

  • 文書を、producer 自身のスクリプトの文脈（Chromium では isolated world）から読みます。 そこでは、ページのスクリプトが文書の読み方を変えられません。
  • 文書を複製し、ページがマークアップの外に持っているものを複製に書き込みます: 各欄の いまの値を value 属性として（textarea では中身として）、 どの box に check が入り、どの option が選ばれているか、開いた shadow root を shadowrootmode 属性つきの template 要素として、ページが adopt した style sheet を style 要素として、各 canvas を それが表示していた画像として。ページが画素を読めなかった canvas は空のまま、 パスワードの欄は値を持ちません。
  • script と noscript の要素、スクリプトを先読みする link 要素（rel="modulepreload"、または as="script" の rel="preload"）を取り除きます。event handler の属性と srcdoc を取り除き、javascript: の URL を javascript:void(0) に置き換えます。リンクはリンクの見た目のまま 残ります。
  • フレームの src はそのままにし、ページが要素に付けた data-browserhive-snapshot 属性は取り除きます。
  • 文書を読めるフレームの要素に来たら、その文書を同じやり方で、同じスクリプトの文脈から、 同じ 1 回の走査の中で写してから、後に続く要素へ進みます。そうしたフレームのうち URL が http・https のものには、来た順に番号を付け、親の複製の中の その要素に、ページが前もって知りえない仮の印（たとえば取り込みごとの乱数を持つもの）を 置きます。1 回の走査なら、複製がその途中で何をしても（shadow root や canvas の 置き換えなど）、番号は要素の順のままです。
  • どのフレームの写しを書くかが決まったら —— フレームの文書に方針を当て、それぞれの写しの 大きさを量った後で —— 仮の印を、そのフレームの写しの URI（属性の値として escape した 形）に置き換え、書かないものでは取り除きます。
  • 文書の doctype を、無かったなら無いまま、もとのとおりに残します。読み手が写しを ページと同じモードで描くようにするためです。
  • 複製の head の先頭に、ページが使っていた文書の base URL を持つ base 要素を置きます。
  • 複製を直列化し、その結果の中のシークレットを、そのままの形と escape した形のどちらも、 隠すシークレットはほかの綴りも、*** に置き換えます。

Screenshots

スクリーンショットは、取り込みのある瞬間に、ブラウザが 取り込みのページを viewport の中にどう表示していたかを写した画像です。producer は スクリーンショットを、そのときまでにブラウザが描いたものから —— そのページのスクリプトと 取り込みの behavior が変えたところは変わったまま —— 取り、オリジンが送ったものからは 作りません。この版が述べるのは、次の時点で取ったスクリーンショットです:

  • after-load —— 取り込みのページが読み込まれて落ち着き、behavior が まだ 1 つも走っていない。
  • after-behaviors —— 取り込みがそのページで走らせた behavior が終わった。

これらは写しの時点で、名前も同じです。1 つの取り込みは、各時点の スクリーンショットを高々 1 つ残し、behavior を走らせなかったときは after-behaviors のものを残しません。1 つも残さなくてもかまいません。 取り込みがどの時点のスクリーンショットを 残したか、ある時点のものを残さなかった理由は、ファイルを収めるパッケージが記録します （[[BROWSERHIVE-WACZ-PROFILE]]）。

producer はスクリーンショットを、一緒に書く 2 つのレコードで記録します: 画像を持つ resource レコードと、画像が何かを述べる metadata レコードです。 metadata レコードは WARC-Refers-To で resource レコードを 名指し、2 つのレコードは WARC-Concurrent-To を持ってはなりません （MUST NOT）。スクリーンショットは交信の一部ではありません。 [[WARC]] はその欄が結ぶレコードに 1 つの日時を持たせますが、スクリーンショットは、その文書を 読み込んだ交信と日時を共有しません。

What a screenshot holds

スクリーンショットの resource レコードの block は、WebP 形式の、動かない 1 枚の画像でなければなりません（MUST）。スクリーンショットを取った瞬間に、 ブラウザが取り込みのページを viewport の中に描いていたものです。主フレームの文書を、 そのページがそこに描いたもの —— 画像や、フレームの文書（別サイトのものも含みます）など —— と一緒に写します。それはブラウザが作ったもので、オリジンのものではなく、読み手はそれを オリジンが送ったものと取ってはなりません（MUST NOT）。

画像は viewport を写し、その先を写してはなりません（MUST）。 scroll して初めて見えるところには届きません。したがって、画像の幅と高さの比は、pixel への 丸めを除いて、viewport の幅と高さの比と同じです。取り込みのページは、viewport の先にある ものを、それが見えるところに来て初めて配置し、多くはそこで初めて取りに行きます。そのページの 全体の画像を取ると、画像のためにブラウザにそれをさせることになります。

画像の大きさは、viewport の大きさからは決まりません。画像の pixel 1 つが CSS pixel 1 つに 当たるとは限らず、device-pixel-ratio は、それがいくつに当たるかを述べません。 その欄が述べるのは、取り込みのページがどの密度に向けて描かれていたかです。比が 2 のとき、 画像は、画像自身の大きさがどうであれ、密度の高い画面のためにそのページが選んだ画像を 写します。画像の倍率は、image-size と viewport の比です。

producer は、画像の中の何も置き換えません。取り込みのページが見せていた値は、 シークレットの値でも、画像の中に在ります。 が 定める出現は、文字とバイト列の中の値の綴りで、画像の pixel はそれに当たりません。

画像は、producer がスクリーンショットを取り始めたときに取り込みのページが持っていた viewport の大きさ、device pixel ratio、scroll の位置で、そのページを写さなければ なりません（MUST）。画像のためにそのどれかを変える producer は、 画像を取った後で元に戻すとしても、そのページに何かをさせ、そのページがしたことは 後に続くレコードに残ります: 取り込みはスクリーンショットの後も続き、behavior が走り、 producer はさらに交信・写し・スクリーンショットを記録します。だから producer は、 そのどれも変えずに画像を取ります。そうすれば、画像を取った後に元に戻すものもありません。 画像を取っている間でも、その後でも、そのページや behavior が自分でそれらを変えることは、 この決まりの外です。

形式が 1 つなら、読み手はどのスクリーンショットも 1 つの decoder で見せられ、block の 先頭のバイト列から、block が Content-Type の述べるとおりのものを持つかを 確かめられます。WebP は、viewport の画像を、取り込みが残す本文に比べて小さく保ちます。

Security and privacy considerations

WARC ファイルは、本仕様が producer に置き換えさせるものと残させないものを除き、wire を 渡ったものを持ちます。request レコードはブラウザが 送ったヘッダの欄を持ち、そこには cookie や認証の情報が含まれることがあります。 response レコードはオリジンが返したものを、その中の個人の情報も含めて 持ちます。

withheld request のレコードは一度も送られなかったリクエストの URL を、 window not opened のレコードは一度も読み込まれなかった文書の URL を持ちます。 どちらの URL も、クエリ文字列に識別子を運んでいることがあります。リクエストを差し止めると オリジンには届きませんが、その URL はファイルに残ります。

写しは、そのときのページの文字を持ち、ページのスクリプトと取り込みの behavior が欄に入れたものも持ちます: パスワードの欄を除き、どの欄の値も写しに 入ります。producer は、そこに見つけたシークレットの値を、少なくともそのままの形と HTML の escape の形で、隠すシークレットの値は が挙げる すべての綴りで置き換えます。それ以外にページが変換したシークレット（たとえばハッシュにしたもの）は 残ることがあり、誰もシークレットと告げなかったものも残ることがあります。写しの document-uri は文書の URL の fragment を残します。fragment はサーバに送られる ことがなく、ログインの手順によっては、ページにトークンを渡すのに使われます。 フレームの写しは、ページと同じ origin のフレームの文書について同じだけを持ち、 シークレットの値は同じように置き換えます。取り込みの方針が文書を伏せるフレームは写さず、 その中のフレームも写しません。

スクリーンショットは、取り込みのページが viewport の中に表示していたものを持ち、 したがって、そのページがそこに描いたものすべての中身を持ちます: 文字、画像、フレームの文書 （別サイトのものも含みます）です。その中身は、それを届けたレスポンスをファイルが持って いるかどうかに関わらず、画像に写ります。ファイルが持たないレスポンスも、本文なしで持つ レスポンスも、理由が何であれ —— 方針でも、大きさの上限でも、シークレットでも （ と を参照）—— そのページには届いており、 そのページがそこから描いたものは画像の中にあります。producer が送らなかったリクエスト （deny）は別です: それについては、そのページに何も届いていません。 スクリーンショットは、そのページの欄が 持っていたものも、behavior が渡した値のうちそのページが表示したものも写します。 本仕様のどの決まりも、pixel の中の値は見つけません: producer がシークレットの値を 置き換えるのは、スクリーンショットのレコードの URI の中で、画像の中ではありません。 そのページが表示した値は、隠すシークレットかどうかに関わらず、画像に残ります。 スクリーンショットの document-uri は、写しのものと同じく、文書の URL の fragment を残します。文字の中の値を置き換えるようには、画像から後で何かを取り除けません。 そうした中身をファイルに残さない手立ては、その取り込みのスクリーンショットを 1 つも 残さないことです。取り込みがいつ 1 つも残さないかは、ファイルを収めるパッケージが 定めます（[[BROWSERHIVE-WACZ-PROFILE]]）。

redacted のレコードは、隠すシークレットの値を、producer が認識できるところで 隠します: ブラウザが送ったものとオリジンが返したものの、URL・ヘッダの欄・文字の本文の中と、 その値に応えて設定された cookie です。 producer は、書き換えられない本文を落とします（ を参照）。 値を置き換えて変わるのはレコードだけで、取り込みの間に起きたことは変わらず、 次のものはそのまま残ります:

  • ページ。behavior は値をページに渡し、ページのスクリプトはそれを読めて、どこへでも送れます。 値が送られた先のオリジンは、それを受け取ります。
  • 値から作られたもの。producer は、値から計算したハッシュや暗号文、 Content-Digest のような HTTP のヘッダの欄の digest を追いません。 オリジンがレスポンスの本文で発行した資格（JSON の token など）も追いません。 それはシークレットで開けたものを開けるかもしれません。 producer が追うのは、producer が見たレスポンスが設定した 8 文字以上の cookie だけです。
  • 出現でない綴り。たとえば、ほかの文字符号の本文の中の、非 ASCII の字を持つ値や、 より長い base64 の文字列の中の値です。
  • 隠すものでないシークレット。取り込みを求めた側が残すことを求めたシークレットの値は、 request・response・metadata のレコードに残ります （写しには残りません。スクリーンショットのレコードの WARC-Target-URI と document-uri にも残らず、producer はそこでも置き換えます）。 スクリーンショットの画像には、取り込みのページが見せていたところに残ります。 取り込みを求めた URL が値を持つときは、その URL を書いた warcinfo のレコードの description にも残ります。
  • 値がそこにあったという事実。BrowserHive-Redacted がどこに何回あったかを述べ、 *** の周り（form の欄の名前など）も残ります。

置き換えは、シークレットより広く届くこともあります。 値に一致する文字は、シークレットと関係があってもなくても置き換えられ、 それを持つ、文字の本文でない本文は落とされます。cookie はこれを起こしやすくします: accepted のような値も、シークレットに応えてレスポンスが設定すれば隠すシークレットに 数えられ、それを送る後のリクエストが、同じようにほかの値を呼び込むことがあります。

本プロファイルを知らない読み手は、*** を送られたものとして読みます。 redacted のレコードの digest はレコードが持つものと合うので、digest から置き換えは分かりません。 レコードから wire を渡ったものを読み取るなら、BrowserHive-Redacted も読む必要があります。

ファイルを人に渡す者は、これらをすべて渡します。写しが除くものと、隠すシークレットのために producer が置き換えるものや落とすものを除けば、本仕様は producer に そのどれかを取り除くことを求めません。取り込みが何をレコードに残さないかは取り込みの方針が決め、方針は ファイルを収めるパッケージが記録します（[[BROWSERHIVE-WACZ-PROFILE]]）。
