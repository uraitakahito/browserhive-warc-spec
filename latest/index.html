This specification profiles [[WARC]]. It states which records BrowserHive writes into a WARC file and what each of them holds, so that a reader holding only the file can tell what the capture recorded, what it left out, and why.

This is a working draft. It describes what BrowserHive writes today. It has no standing beyond that project and is not endorsed by the publishers of [[WARC]].

Up to its version 1.15.0, [[BROWSERHIVE-WACZ-PROFILE]] held the rules for the WARC records BrowserHive writes. They moved here so that a WARC file can name the rules it follows by itself (see ), and so that a file read apart from its package still means what it says. BrowserHive WACZ Profile 1.16.0 requires the WARC files of a package to conform to this version.

[[WARC]] defines a WARC-Profile header field, which says how a revisit record is to be read. This specification has nothing to do with that field.

Introduction

[[WARC]] says how records are framed and which header fields they carry. It leaves to the writer what to put in a payload, which records to write about a body it did not keep or a request it did not send, and how to say why. A reader of a BrowserHive WARC file needs those answers, and they are knowable only while the file is being written.

This profile fixes them. It changes nothing [[WARC]] says: the records it adds are metadata records, which a reader unaware of this profile can pass over.

BrowserHive writes its WARC files into a WACZ package, whose rules are in [[BROWSERHIVE-WACZ-PROFILE]]. The rules here concern only what a single WARC file holds, so that they still hold for a file taken out of its package.

Conformance

The conformance target of this specification is a WARC file: a single file. Conformance is a property of files, not of the software that writes them.

A conforming file is a conforming [[WARC]] file. This specification adds requirements. It removes none, and it relaxes none.

Where this specification uses the terms MUST, MUST NOT, SHOULD and MAY, they are to be interpreted as described in [[RFC2119]].

The producer is the software that writes the file. A capture is one run of the producer against one page. A capture writes one or more WARC files.

The warcinfo record

Each WARC file MUST begin with a warcinfo record whose WARC-Filename is the name of the file that holds it. Its application/warc-fields body MUST contain the fields below marked as required.

FieldRequiredDescription
conformsToyes The URL of the version of this specification the file claims to satisfy. For this version, https://uraitakahito.github.io/browserhive-warc-spec/1.0.0/. The field MUST appear exactly once.
formatyes WARC File Format 1.1.
softwareyes The producer and its version.
robots-policyno ignore: the producer does not consult robots.txt. Whether a page is to be captured at all is for whoever asks for the capture to decide.
descriptionno Free text that says what was captured.
 
WARC/1.1
WARC-Type: warcinfo
WARC-Record-ID: <urn:uuid:0b7e8a52-6a63-4f0e-9d0b-6f1c2a3e4d5f>
WARC-Date: 2026-11-01T02:14:31.882Z
WARC-Filename: data-000.warc.gz
Content-Type: application/warc-fields
Content-Length: 203

software: browserhive/22.1.0
format: WARC File Format 1.1
conformsTo: https://uraitakahito.github.io/browserhive-warc-spec/1.0.0/
robots-policy: ignore
description: Capture of https://shop.example/

conformsTo names this profile, not [[WARC]]. The base format is named by format, and every conforming file is a WARC 1.1 file (see Conformance). A single declaration leaves a reader nothing to choose between. A reader MUST NOT infer conformance to a version of this specification from anything other than conformsTo.

Records and files

A record MUST NOT span two files: a record is written whole into one file, and the producer writes no continuation records. The records of one exchange MUST be in the same file.

A capture may write more than one file. How those files are named, and when the producer starts a new one, are rules of the package that holds them, not of a single file. See [[BROWSERHIVE-WACZ-PROFILE]].

Exchanges

An exchange is one request the browser sent and the response it received to it. The producer records an exchange as a request record and a response record, and, when the response is recorded without its body, a record of a body not kept. The request record and the response record MUST each name the other in WARC-Concurrent-To.

The records of one exchange MUST carry the same WARC-Date: the time at which the browser began the request, as the browser reported it. A response that redirects ends its exchange. The request that follows the redirect begins another exchange, with its own time.

The payload of a response record MUST be in HTTP/1.1 form [[RFC9112]], whatever protocol version carried the exchange: a status line, then the header fields, then the body.

[[WARC]] has the date of a record be the moment its capture began, and has the records of one capture event share one date. For an exchange, that moment is when the browser began the request. The time at which the producer assembles the records is later by however long the body took to arrive, which for a large body can be minutes, and it says when the producer wrote rather than when the page was fetched.

Existing readers of WARC files parse the payload of a response record as HTTP/1.1. An exchange carried over HTTP/2 or HTTP/3 is therefore written in HTTP/1.1 form, and the protocol version that carried it is not recorded in the payload.

Payloads

A browser turns a text body into characters before anything else sees it, and hands it to tools as characters. Written back out as bytes, the result is the body in whatever encoding the writer chose — not the one the origin sent, unless the two happen to agree. The requirements in this section keep the payload of each record to the bytes that crossed the wire, so that a payload digest vouches for what the origin and the browser sent.

Response payloads

The payload of a response record that holds a body MUST be the bytes the server sent, with the content-coding named in its Content-Encoding removed and nothing else changed. In particular, a producer MUST NOT convert a text body from one character encoding to another: a body sent in Shift_JIS is stored as those Shift_JIS bytes, and a body whose media type declares no charset is stored as it was sent, whatever charset a browser would have read it with.

A data: URL is sent by no server. Its payload is the data the URL carries, decoded as the URL defines (base64, or percent-encoding as bytes), and likewise not converted.

A producer that cannot obtain a body as bytes MUST NOT store one rebuilt from decoded text. It records the response with an empty payload and a record of a body not kept whose truncated is not-intercepted.

Request payloads

The payload of a request record that holds a body MUST be the bytes the browser sent as the request body. A producer that cannot obtain them as bytes MUST NOT store a body rebuilt from decoded text; it records the request without one.

Records of bodies not kept

For each response recorded without the body the server sent, other than a response that has no body to send (one to a HEAD request, and status 1xx, 204, 3xx and 304), the file that holds the response record MUST also hold a metadata record, hereafter a record of a body not kept. Its WARC-Target-URI MUST be the URL of the response, its WARC-Refers-To MUST be the WARC-Record-ID of the response record, and its application/warc-fields body MUST contain:

FieldRequiredDescription
truncatedyes Why the record holds no body. One of the values below.
encodedDataLengthno The size of the whole response as it crossed the wire, in bytes, when the producer knows it.
  • too-large — the body was larger than the limit the producer placed on a single body.
  • task-cap — keeping the body would have taken the bodies the capture kept past the limit the producer placed on all of them.
  • url-policy — a URL policy of the producer said to keep the exchange without its body.
  • content-type — a media type policy of the producer said to keep no body of the response's media type.
  • not-intercepted — the body crossed the wire, but the producer could not obtain it as bytes (see ).
WARC/1.1
WARC-Type: metadata
WARC-Target-URI: https://example.com/api/feed
WARC-Date: 2026-10-30T02:14:31.882Z
WARC-Refers-To: <urn:uuid:5c1f0b8e-2a77-4a5e-9d3e-0f6f3b1d2c4a>
Content-Type: application/warc-fields
Content-Length: 53

truncated: not-intercepted
encodedDataLength: 4821

The response record of a body dropped at a size limit (too-large or task-cap) MUST carry WARC-Truncated: length, and that of a body that was not intercepted MUST carry WARC-Truncated: unspecified, so that a reader of the WARC file alone does not take the empty payload for the body.

A body a policy omitted was not cut short, so its response record carries no WARC-Truncated. Which limits and policies were in force is recorded outside the WARC file, by the package that holds it ([[BROWSERHIVE-WACZ-PROFILE]]).

Records of withheld requests

For each request the producer withheld by a policy, a WARC file of the capture MUST contain a metadata record, hereafter a record of a withheld request. Its WARC-Target-URI MUST be the request URL, and its application/warc-fields body MUST contain:

FieldRequiredDescription
actionyes What the producer did. deny: it did not send the request, so nothing left the capturing machine for that URL. no-archive: it let the request go and the origin answered, but it kept nothing of the exchange beyond this record. This is the field that says whether the request was sent.
patternyes The pattern that matched, spelled exactly as the producer's policy spells it, so that a reader can find it there.
methodyes The request method.
resourceTypeno What the page was fetching, when the capture knows it.
targetno What made the request: page, iframe (a frame the browser runs apart from the page, typically one from another site), worker or service_worker. Absent when the capture does not say.
 
WARC/1.1
WARC-Type: metadata
WARC-Target-URI: https://www.example-analytics.com/collect?v=2
WARC-Date: 2026-09-06T02:14:31.882Z
Content-Type: application/warc-fields
Content-Length: 87

action: deny
pattern: *://*.example-analytics.com/*
method: POST
resourceType: XHR

A deny reaches every request the capture causes, so its record MUST be written whichever part of the page made the request, including parts whose traffic the producer does not otherwise record.

A record of a withheld request carries no response and no body. It asserts that the page asked for the URL and that the producer decided what to do about it — not that the request failed, and not that the origin returned nothing. A capture that could not reach an origin MUST NOT report it this way.

A policy that keeps the exchange but not its body produces no record of this kind. The request and response records are written as usual, and the absent body is reported by a record of a body not kept whose truncated is url-policy — never as dropped at a size limit.

Records of windows not opened

A capture records one page, and the producer does not give the page a new top-level browsing context — a window or a tab ([[BROWSERHIVE-WACZ-PROFILE]]). For each time the page asked for one, a WARC file of the capture MUST contain a metadata record, hereafter a record of a window not opened. Its WARC-Target-URI MUST be the URL the window would have loaded, as the browser reported it: about:blank when the page named none, and the action URL, without the submitted body, when a form asked. Its application/warc-fields body MUST contain:

FieldRequiredDescription
windowyes not-opened. This version defines no other value.
windowNameno The name the page gave the window; _blank when it gave none. Absent when the page asked through a navigation that names no window, such as a click carrying a modifier key.
targetno What asked: page, or iframe (a frame the browser runs apart from the page, typically one from another site). Absent when the capture does not say.
 
WARC/1.1
WARC-Type: metadata
WARC-Target-URI: https://shop.example/campaign?from=top
WARC-Date: 2026-10-01T02:14:31.882Z
Content-Type: application/warc-fields
Content-Length: 54

window: not-opened
windowName: _blank
target: page

No request was sent for the window's document, so nothing left the capturing machine for that URL. The record is written whether or not a URL policy of the producer matches the URL, and it carries no action: it is not a record of a withheld request, and a reader MUST NOT count it as one.

Security and privacy considerations

A WARC file holds what crossed the wire. Its request records hold the header fields the browser sent, which may include cookies and credentials, and its response records hold what the origins returned, including any personal data in it.

A record of a withheld request holds the URL of a request that was never sent, and a record of a window not opened holds the URL of a document that was never loaded. Both URLs may carry identifiers in their query strings. Withholding a request keeps it from the origin; it does not keep its URL out of the file.

Whoever passes a file on passes all of this on. This specification does not ask the producer to remove any of it. What a capture keeps out of its records is decided by the policies of the capture, which the package that holds the file records ([[BROWSERHIVE-WACZ-PROFILE]]).
